## MC-02 — Concurrent capability observations and probe ordering

The initial record-ID ordering design was revised after architect review: network probe start order can differ from completion/record order. Migration016 is used by test lanes; preserve its bytes/checksums and add018 after017. No production database or service operation is authorized by source work.

Add a protected capability_probe_reservations table with database-generated monotonic reservation_id, source_id FK, globally unique request_id, source_row_version and DB-clock reserved_at. It is writable only through security-definer functions, with PUBLIC/app/admin/control direct access revoked. The reservation function acquires the same per-source advisory transaction lock and validates enabled source/current row version before allocating or reusing an ID. The writer alone gets reserve_capability_probe(source_id,request_id,source_row_version); acceptor authority and accepted-reader ACL remain separate. Every observer must reserve before invoking onec.capabilities. Reservation is bound to exact registered source/request/version and survives a live retry. It is not caller/model-supplied identity or provider freshness proof.

Upgrade existing observation rows non-destructively: create one corresponding reservation per captured existing row in deterministic order with its existing observed_at/source/version. Add a nonnull unique reservation_id FK on observations and preserve their original observation_id, payload and accepted pointer. Change singleton primary key(source_id) to(source_id,request_id), retaining global request_id and observation_id uniqueness. Add source/expiry indexes. Acquire schema lock with bounded lock_timeout; transactional failure leaves017 intact. No row is dropped to widen the key.

The observer passes the exact returned reservation_id into a new record function signature. Revoke/remove the old record signature so an old worker cannot continue its source-wide delete. Runtime exact schema version becomes18, so all old workers are stopped before disposable upgrade. Public HTTP refresh/accept/read signatures stay unchanged. Update writer-role checks for new reserve and record functions; no app/control/acceptor reservation or record authority is granted.

Under the existing per-source advisory transaction lock and enabled-source FOR SHARE/version check: reserve reuses the same live exact-request reservation. An expired pending reservation may be replaced with a new ID after cleaning its expired unaccepted observation. A stale probe retains its old ID; it cannot record under a later reservation created by a retry because record validates exact source/request/version/reservation ID. Current accepted request keeps its accepted observation and reservation even beyond five minutes; a matching retry can return the same observation, not a new provenance claim. Configuration-version mismatch refuses instead of rebinding the old request.

Record requires the exact existing reservation, verifies its DB expiry unless returning an already accepted matching observation, and inserts/reuses only its own source/request row. Live pending or current accepted rows of other requests cannot be deleted. A different request can remain pending concurrently. The physical probe is outside a DB transaction; no SQL lock is held across 1C or acceptor HTTP I/O.

Accept serializes by source and validates writer provenance, current source version, pending TTL and exact source/request/observation/reservation. A candidate reservation older than the current accepted observation's reservation returns no row and cannot mutate capabilities or drift. Newer pending reservations alone do not block an earlier result: a crashed pending probe cannot starve valid work. Test the critical interleaving: reserveA, reserveB, B records/accepts, A finishes/records/accepts; A must not replace B. Ordering is DB-issued reservation order, not authenticated provider-history freshness.

The read function remains latest-only and binds exact observation ID/request to the current source_capabilities pointer and enabled source/version. B may supersede A before A reads, in which case A fails closed. No success is promised for historical reads after supersession. Empty acceptance continues the existing409 path and observer503 mapping; no invented READY or permissive fallback.

Retention stays bounded by a five-minute live window with cleanup on record/reserve calls: delete only expired noncurrent capability-cache observations and then expired unreferenced reservations. Preserve the current accepted observation/reservation regardless of age, plus every live pending row. These are ephemeral capability-cache rows previously deleted wholesale, not business data or the append-only audit ledger. Source advisory lock and FK ordering protect concurrent cleanup; no periodic job is installed. A killed probe's old reservation cannot be reused after replacement.
