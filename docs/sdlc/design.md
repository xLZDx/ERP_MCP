The period reader is a real adapter boundary, not a boolean mapper. Repository evidence cited by the current finisher scope does not identify a qualified period endpoint, query, or source contract. Implementation must use a configured read-only source operation whose meaning is evidenced for that source (for example, an approved metadata-bound COM/extension read); it must not guess a register or infer openness from proposal dates. Until that source operation and authentication are established, return an unavailable/unproven typed observation and preserve fail-closed apply behavior. Do not describe such a refusal path as a working real-data producer.

The budget producer has a concrete authoritative source: the ledger's scoped grant and reservation state. It computes remaining amount from the grant limit less reserved and consumed amounts under the same serialization/locking contract used by the existing budget routine; the reader must not use a stale application cache. The ledger remains responsible for the final atomic decision.

## 3. S12/S13 data flow and consistency

### 3.1 SQL catalog and exhausted grant

Migration 028 is additive and versioned after migration 027. It mirrors the exact canonical Python refusal-code set (39 entries), including `PERIOD_CLOSED` and `GRANT_EXHAUSTED`, and updates only the SQL budget branches required to distinguish the new exhausted case. It does not edit historical migrations or change approval-digest bytes. Registry equality is a vocabulary check, not proof that SQL can construct every Python refusal. This design explicitly classifies `AMOUNT_INCONSISTENT` as Python-only because proposal amount parsing is above the ledger, and `PERIOD_CLOSED` as source-observation-dependent because SQL cannot perform the authenticated 1C read. SQL may contain these catalog values for shared vocabulary, but does not claim to produce them. The migration change record must reconcile all 39 codes against actual SQL raise sites and name any additional Python-only emissions; it must not imply those two codes are SQL-produced.

For a positive requested amount, compute the effective grant remainder using the existing grant semantics, including already consumed and reserved amounts and the existing effective amount rules for POST. Return `GRANT_EXHAUSTED` only when the grant has zero or negative remainder. A positive request larger than a nonzero remainder, a request outside the grant window, an unknown/inactive grant, and fail-closed `NOT_CHECKED` continue to map to `BUDGET_EXCEEDED` as required by the S12 amendment. A zero-amount request against a fully consumed grant remains allowed. Check ordering, locks, transaction boundary, and idempotent reservation behavior remain those of existing ledger routines.

### 3.2 Period and budget evidence

Evidence is represented as a typed snapshot, not caller-supplied booleans. The boundary carries source ID, company/tenant scope, target period, authenticated principal/source identity, source observation time, source version or state fingerprint, and one parsed period state (`OPEN`, `CLOSED`, or `UNKNOWN`). The adapter constructs it only from one authenticated response. The producer derives `period_observed_open` or `period_closed` for the existing `BeginApplyEvidence` contract only after validating scope, freshness, internal consistency, and target version. `OPEN` and `CLOSED` are mutually exclusive; `UNKNOWN` never becomes open. At apply time, stale or changed target state is rejected by the existing fingerprint/digest guard. The current S12 ordering continues to return `PERIOD_CLOSED` only for a positively observed closed period and refuses missing/non-open evidence before any writer call.

Budget evidence is derived from a scoped ledger snapshot containing grant identity/status, currency/window, limit, reserved, consumed, and requested amount. It produces `BudgetCheck.EXHAUSTED` only when the observed grant remainder is non-positive and the requested amount is positive. Other denial causes retain the existing checks and `BUDGET_EXCEEDED` mapping. The SQL ledger rechecks and reserves atomically; the snapshot alone never authorizes a write.

### 3.3 In-flight list and status

The operator list reads current in-flight records from PostgreSQL ledger/service state through the existing scope-bound asyncpg adapter. Each row has only the fields needed to identify the change and its current lifecycle status. Status-by-ID uses the existing `read_status` routine (`src/business_ai_gateway/phase2/change_ledger/sql_ledger.py`, `read_status`, around line 883) under the same tenant/company authorization scope. The list and subsequent status read are separate observations: status may advance between them, so clients must treat status-by-ID as current state, not a snapshot transaction shared with the list. Unknown, out-of-scope, or unreadable IDs use the established safe refusal/absence semantics. No test fixture, process cache, or unscoped table query supplies this interface.

## 4. S16 isolation and ports

S16 is a new isolated `src/erp_mcp_s16/` package. It may depend on stable S12 value/transition contracts through explicit typed ports, but does not import or call the Phase 2 writer, gateway composition, or private listener. Neither the gateway nor writer imports S16 in this sprint. The S16 core contains self-approval checks, nonce single-use, canonical preview-digest binding, version/expiry checks, token-class checks, apply-time revalidation, and claim-once orchestration. Persistence, clock, randomness, target inspection, verification, and claim storage are injected ports; fakes may provide state but may not implement or bypass core policy. The preview is generated as `canonical_preview_bytes` and hashed separately into `preview_digest`; the internal S12 approval envelope binds that digest together with the raw approval nonce. Raw nonce and CSRF secret/state stay server-side. The browser receives only an opaque random, single-use `decision_ref`, bound server-side to the approver session, principal, company/source scope, target version, preview digest, and expiry. It is a browser decision/CSRF replay capability, not the internal nonce or CSRF secret. Every approval POST also requires exact `Origin` and `Referer` validation.

The model-facing surface contains exactly `propose`, `status`, `apply`, `verify`, and `rollback_propose`. An already-authenticated typed principal and disjoint token class enter the core; identity, approval, CSRF, nonce, and write authority are not inferred from request-body fields. `verify` passes the S15 verifier result through unchanged; POST/UNPOST shapes remain `UNSUPPORTED_SHAPE`. `rollback_propose` only creates a separately approved UNPOST proposal for a verified POST based on a current target observation. Rollback of CREATE_DRAFT and UNPOST is refused as `ROLLBACK_REFUSED`. Approval is a separate approver-session path, not a model tool or alias. Apply revalidates the base fingerprint, principal epoch, approver validity, target/base binding, kill switch, and one-time claim immediately before the apply port. A valid approver session requires no per-decision reauthentication before its expiry; the 15-minute idle and absolute lifetime are both enforced.

Private-listener authentication is positive authentication on every request; loopback or private-network origin is not identity. Any private ingress configuration remains inert in this sprint: no listener is started, no process route is registered, and the production binding set stays empty. When a later authorized deployment uses the boundary, the default is loopback and any private ranges must be explicitly configured; public/tunnel/proxy/redirect paths are refused. Hand-authored client-shape transcripts are labelled not observed and are not connector evidence.

## 5. Deployability, migration, and recovery

Migration 028 is forward-only and additive: apply through the existing ordered migration mechanism, verify registry equality and exhausted-budget behavior, and retain migration 027 as the rollback point only before 028 is applied. After application, rollback is a forward corrective migration; do not remove or rewrite migration history. No S16 database schema or production persistence is added. S16 rollback is removal/revert of unwired library code; because no route or listener is bound, there is no runtime cutover or data migration.

SQL list/status and budget operations stay within existing asyncpg transaction and scope ownership. Do not combine external 1C reads and SQL reservations into a presumed distributed transaction. The period observation is an external read followed by a local revalidation against the target fingerprint at apply; uncertainty or mismatch stops before the writer boundary. The writer remains disabled, so this sprint does not claim cross-system atomicity.

Operational evidence must separately identify migration application/parity, source observation provenance and freshness, SQL ledger results, and S16 fake results. Missing source access, credentials, unsupported source semantics, listener/client/IdP availability, or formal upstream acceptance are recorded as `NOT_RUN`/`UNKNOWN` with the exact dependency. Do not promote code-level implementation to runtime-proven or live-qualified status.

### Evidence vocabulary

`Designed` means the contract is specified here. `Implemented` requires an observed source diff. `Manually reviewed` requires a named review against an exact revision. `Runtime-proven` requires an observed run against the stated environment and exact revision. `NOT_RUN` names a required scenario for which no current evidence exists. None of those states is interchangeable.
