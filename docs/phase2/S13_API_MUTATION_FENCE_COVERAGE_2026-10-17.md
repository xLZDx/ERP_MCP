# S13 API mutation and lifecycle-fence coverage — 2026-10-17

## Scope and evidence boundary

This is a repository-source inventory of change-ledger APIs and write surfaces in migrations 004–026. It is based on source review only; it does not establish installed grants, effective production privileges, deployed service paths, or physical-writer behavior. SQL adapter calls use one transaction each, set a local role and tenant/company scope, and reject an already active caller transaction (`src/business_ai_gateway/phase2/change_ledger/sql_ledger.py:165–203`). The synthetic coordinator invokes the writer only after the SQL call returns (`simulation/synthetic_dispatch.py:88–124`).

The table groups APIs by mutation contract rather than listing cryptographic and formatting helpers. `SqlChangeLedger.SPEC` labels principal classes (such as `requester` and `writer`), not PostgreSQL role identifiers; configured role names come from the actor mapping and migration grants. These labels are not assigned people.

## Trigger, grants and direct-table boundaries

- Migration 022 installs `events_lifecycle_fence_guard` on event insertion. It locks the scoped lifecycle row `FOR SHARE` and rejects missing, `NOT_READY` and `RECOVERING` state; `LEGACY` remains accepted for compatibility with migrations 001–021. Migration 024 applies a bounded wait and restores the caller's prior `lock_timeout`.
- Migration 022 fences permit insert/update, captures epoch on insert and rejects stale epoch or `NOT_READY`/`RECOVERING` lifecycle state while retaining `LEGACY` compatibility. Migration 012–013 dispatch guards and migration 016–018 receipt guards protect their own invariants; they are not equivalent to every-mutation coverage.
- Migrations 004–006 revoke broad `PUBLIC` table/function privileges; runtime behavior is exposed through granted functions with scoped RLS/policies. Direct SELECT grants are role-specific. Owner, migration and administrative capabilities are separate trust boundaries. Source anchors: `004_change_ledger.sql:1391+`, `005_change_registry.sql:1306+`, `006_change_sweeps.sql:907+`.
- Direct record, registry, evidence, budget, hold, key and observation writes that do not produce a fenced event or touch a guarded permit can bypass lifecycle triggers while still using their granted scoped function. The reviewed source does not show a universal per-table fence trigger on all mutable tables.
- `budget_reserve`, `budget_consume`, and `budget_release` are internal helper functions invoked by granted APIs; they are not caller-facing runtime API entries. The matrix groups public APIs; exact role grants must be checked against each migration and actor mapping. Effective deployed privileges remain unknown.

## Lock and transaction observations

1. Migration 008's historical ledger lock-order text is named namespace advisory locks first; claim-token rows before records; secondary rows after their owning record; event-chain advisory lock last. A transaction already holding the chain lock must not wait for rows. **Implementation candidate correction (2026-10-23):** this fixed relation order is superseded by the schema-derived FK-SCC contract in `S13_SCOPE_FENCE_IMPLEMENTATION_DESIGN_2026-10-22.md`. Current DDL has `targets → records` and `records → claim_tokens`, as well as a self-referencing `records` SCC; a literal claim-token-before-record order cannot satisfy the FK graph. This note records the prior migration wording and does not approve or activate a replacement migration.
2. Migration 022/024 event and permit triggers acquire a lifecycle-row shared lock within the short API transaction. Migration 023 revokes the worker recovery grant and replaces the recovery function with a refusal, so no supported runtime recovery transition currently exercises the exclusive side. The five-second bound covers lifecycle-row lock acquisition, not the whole transaction, sink I/O or writer call.
3. Permit/dispatch ordering remains guarded by 006–008 and 012–013. These checks finish in SQL before the physical writer accepts a call; the call may be accepted or finish after database transaction end.
4. A future common scope fence must be acquired consistently before row locks without breaking the candidate global advisory order or schema-derived FK-SCC row order. The current S13 candidate makes that scope fence exclusive for every mutation and recovery transaction; it remains unimplemented and requires source-wide review on every mutation path. The signature-level source edges and remaining competing-writer gaps are mapped in [`S13_SOURCE_FINAL_GRANT_AND_LOCK_INVENTORY_2026-10-22.md`](S13_SOURCE_FINAL_GRANT_AND_LOCK_INVENTORY_2026-10-22.md). An event-trigger-only change is insufficient.

## Conclusion and next action

The lifecycle fence in migrations 022–024 is deliberately partial: event and permit triggers would serialize their attached writes against a lifecycle-row state update, and the writer-epoch API provides a short-lived check. Migration 023 disables the supported recovery entry point, so no runtime recovery transition is active. The design does not cover every mutable table/path and does not span external I/O. Keep recovery-start refusal and lifecycle `NOT_READY`.

Before proposing a migration, have the database reviewer reconcile this per-API matrix with the full function/grant inventory and confirm an implementable lock order. The actual licensed service/channel owner must then demonstrate writer-side epoch installation, idempotent lookup by stable call ID, and a quiescence barrier that rejects delayed old claims while accounting for already accepted/in-flight calls. No such owner or capability is established by repository evidence.
