## Scope decision

S7 takes only what can be built and tested OFFLINE, as unwired reference modules over fake ports (new files only; the existing modules above are touched only for a defect proven by a failing test, same rule as S6 E3 and S6b): a Drive port `Protocol` with a scripted fake (`changes.getStartPageToken`, `changes.list` with start page token / next page tokens / new start token, `files.get` metadata, `revisions.list`), an ERP_MCP-owned OAuth/consent state machine with an in-memory token store that holds only fake tokens, a least-privilege scope evaluator, a baseline-with-start-token orchestrator with a durable fail-closed cursor model, and revision/move/removal/auth-expiry handling. Everything that needs the real Google OAuth client, consent screen, real tokens, a real Drive folder or shared drive, real quotas, real refresh against Google, secrets storage or real watch channels stays NOT_RUN and operator-owned (listed below).

Design decisions fixed here (so reviewers can falsify them):

1. ERP_MCP-owned consent. The flow has its own client identity, its own requested scope set and its own consent record per (tenant, connection). It never reads, copies, refreshes or compares PDCC or Release 1 tokens or rights: the token store is a new in-memory class keyed by ERP_MCP connection id, the state machine takes no token from any other store, and the boundary test (E5) proves by AST that no S7 module imports Release 1, PDCC or the existing HTTP reader. Rights granted to another system on the same Google account confer nothing here.
2. Least privilege is a property of the REQUESTED scope set, evaluated by name: the evaluator accepts only an allow-list (a narrow per-file / file-picker style scope and a read-only metadata/readonly scope) and refuses any broad scope (full drive, all-files readonly treated as "folder isolation") unless the consent record carries an explicit `BROAD_ACCEPTED` risk label. A broad token is never reported as folder isolation: the isolation claim is `APPLICATION_FILTER_ONLY` and the evidence class says so (TC105). Whether a real narrow scope actually reaches new children of a folder is an open real-world question (G4); offline we model both outcomes in the fake and the module reports `NEW_CHILD_ACCESS` as PROVEN only from a scripted observation, never by assumption (TC104).
3. Folder/shared-drive scope is an explicit corpus declaration: (account namespace, optional shared-drive id, root folder ids). Namespaces are separate keys `account:<id>` and `drive:<id>`; the same raw file id under two namespaces is two different objects (TC107). A file is in scope only if its current parent chain (resolved from fake `files.get` metadata, bounded depth, cycle-safe) reaches a declared root; a shortcut is never followed as a membership proof and a move out of the corpus is a scope escape, not a rename (TC110).
4. Start page token before baseline: the orchestrator obtains `getStartPageToken` FIRST, records it durably, only then lists the baseline; the catch-up reads `changes.list` from the recorded token until a terminal `newStartPageToken`; changes that happened during the baseline are therefore not lost (TC106). Page tokens are opaque exact strings, never normalized.
5. Durable fail-closed cursor: the cursor record has states `UNINITIALIZED`, `BASELINING`, `CATCHING_UP`, `LIVE`, `GAP`, `AUTH_REQUIRED`, `RESNAPSHOT_REQUIRED`; the page and the cursor advance are committed together through the existing cursor CAS contract with job/fence (the cursor is advanced only by the durable caller via `committable_cursor()`, as `drive_changes.py` already requires); any unknown change kind, token regression, repeated token, identity/corpus change, lost or corrupted cursor, or lost lease stops advancement and moves to GAP / RESNAPSHOT_REQUIRED through `ResnapshotTracker`; a fail-closed state is never silently reset to LIVE (TC108). Per `CONTRACTS_AND_API_RU.md` section 6 no regular Drive-cursor expiry is invented: lost/corrupt/identity/corpus change are the recovery triggers.
6. Revisions: a new revision of an attested file produces a new UNATTESTED candidate and the older PASS stays HISTORICAL, never "latest" (TC109). Revision history is requested only through a read call; if the fake reports history forbidden (readonly/Viewer) the result is `HISTORY_UNAVAILABLE` with coverage "current only", and no right elevation or keepForever mutation exists anywhere in the port (the port has no write method at all).
7. Removal gives a tombstone and a requalification signal, never a guessed replacement by name/size/hash similarity (TC111).
8. Auth: `invalid_grant` (modeled as a fixed fake error code, with the reason string never echoed), revoked consent and expired access token are three distinct states; refresh-token revocation leads to `AUTH_REQUIRED`, pauses the connection through `SourceStateMachine`, emits an alert record (fake alert sink) and blocks every Drive port call fail-closed until a new consent; revoke removes the stored fake tokens, bumps the scope epoch and invalidates cursors bound to the old epoch (no resurrection of old grants on reconnect, same rule as TC015). Webhook/watch notifications are accepted only as a HINT that schedules a poll; they never carry data, never advance a cursor, duplicates/out-of-order are idempotent, and polling alone is complete (TC113, TC114).
9. Capture default stays OFF in prod: Drive capture goes through `capture_permit.py` mode/window rules; S7 adds no permit logic of its own and a missing/expired permit refuses.
