# S13 private writer service design for Ivan's licensed lane

Date: 2026-10-22  
Status: operator-authorized engineering design; implementation and runtime qualification remain open.  
Accountable task owner: operator. Technical owner of the Ivan host/connection boundary: the Ivan stack (`ERP_MCP_Ivan_Stack`), as recorded in `artifacts/REMOTE_1C_HOST_STACK_2026-10-11.md`. Codex is the delegated executor.

## Decision and scope

Build the S13 physical writer boundary as a separate private service on Ivan's licensed Windows lane, beginning with a disposable clone of `818HA_p2diff`. It must be reachable only through loopback or an authenticated, ACL-restricted Tailscale path; it must never be exposed through the public MCP tunnel. The service provides durable call-ID idempotency, rejects stale epochs at admission, offers authoritative outcome lookup by the immutable call identity, and implements a quiescence barrier that is serialized with admission. It does not add write methods to the public/read-only gateway.

This decision authorizes local implementation and qualification on disposable copies. It does not authorize deployment, writes to any live company base, or a claim that the current COM channel already supplies the required atomicity. Production authorization remains `NONE`; S13 and release gates remain open until their recorded acceptance evidence exists.

## Contract inherited from S12

The service is downstream of the frozen S12 contract in `S12_CONTRACT_FREEZE_V2_2026-10-16.md` and `S13_WRITER_BOUNDARY_CLAIM_AND_RECOVERY_CONTRACT_2026-10-17.md`:

1. The ledger durably commits the one-time `PERMITTED -> DISPATCHED` CAS and its audit event before physical I/O. The immutable identity includes the full scope tuple, `change_id`, generation, `call_id`, operation, target, epoch, and approved payload digest.
2. The service accepts a call ID at most once. An identical retry returns existing status; a conflicting identity or stale epoch is refused. An accepted call is never reissued to COM after timeout, disconnect, response loss, or restart.
3. The service's outcome lookup is authoritative only for its own durable accepted-call journal and bound service instance. It cannot claim that an effect occurred or did not occur based only on a marker, timeout, missing row, process exit, or absent response.
4. Recovery serializes a scope-wide epoch advance with new call acceptance, rejects delayed requests from older epochs, and enumerates calls accepted before the barrier. Every enumerated call must have independently established terminal evidence before readiness can advance. Any unknown, queued, or possibly executing call leaves the scope held and `NOT_READY`.
5. No PostgreSQL transaction or row lock spans checkpoint-provider I/O or COM. The application gateway remains read-only; only this separate private service may own the licensed COM write identity.

The S12 signed `DispatchReceipt`, independent `OutcomeEvidence`, `CompletionProof`, canonical payload rules, and operation scope remain distinct requirements. This design does not replace them with the service journal or the 1C marker attributes.

## Service boundary and ownership

The service is a separate process and deployment unit from the existing MCP gateway and `testlane.phase2_mcp` comparison server. Its only initial target is an isolated copy of `818HA_p2diff`; it must authenticate the base and verify its configured fingerprint before accepting any write-capable request. It uses the least-privilege `CT14Писатель` account and the already approved COM route. OData writes, public-tunnel ingress, administrator credentials, hard deletion, and writes to the immutable data template are out of scope.

The Ivan stack is the technical owner of host execution and the private connection boundary. This does not establish a separately named human service contact. The operator remains accountable for the delegated task. Database, security, reliability, functional-test, and E2E roles retain their review/test responsibilities; role names are not people.

### Caller-authentication candidate

The initial private ingress uses the repository's existing JWT verification mechanism, with the
fixed audience `urn:erp-mcp:private-writer`, the distinct scope `erp_mcp:private_writer`, and an
explicit allowlist of client IDs. The authenticator must reject missing/duplicate bearer headers,
wrong audience or scope, expired tokens, disallowed clients, and verifier failures before admission.
The gateway's local-development principal fallback is not reusable for this boundary. This fixes a
local protocol candidate; it does not establish that the IdP has provisioned the audience, scope,
or any authorized writer client. The caller token authenticates the requesting client only and does
not replace S12 ticket/permit verification, PostgreSQL grants, or COM-side entitlement checks. The
listener remains absent and unqualified until those identity/configuration dependencies and the
loopback/Tailscale binding are verified.

The first transport candidate is a loopback-only ASGI HTTP adapter with separate authenticated
`dispatch` and exact-ticket `lookup` routes. Its request parser is bounded and rejects duplicate
JSON keys before typed validation. The app factory does not start a process; the service must finish
durable startup recovery and satisfy deployment gates before any server binds. Tailscale ingress is
not implemented by this candidate because interface ACL ownership and caller provisioning remain
unverified. The current source candidate requires `ConfiguredPrivateWriterAuthorizer`, which binds
each verified OAuth client-ID/subject pair to an explicit set of exact
tenant/company/organization/base-fingerprint tuples. Dispatch additionally calls the injected
trusted writer verifier for the ticket and signed permit before admission within a bounded
five-second verifier deadline; the service repeats its own checks before durable admission. Lookup
checks the caller's exact scope but deliberately does not require a still-unexpired permit: it can
only return the exact immutable identity found through the service's durable lookup, and it never
dispatches. This preserves recovery lookup after expiry without treating caller-supplied fields or
the token signature as authority. The per-client grants, verifier provenance, IdP provisioning, and
listener remain unconfigured and unqualified; the app factory refuses construction without the
authorizer and does not bind a socket.

## Admission, idempotency, lookup, and barrier

### Durable admission

Admission uses a new additive, versioned S13 contract; it does not edit migrations 022–024 in place or assume that the preparatory lifecycle API can enter recovery. It requires a fresh top-level `READ COMMITTED` transaction set as the first SQL command after `BEGIN`; unsupported isolation aborts before fence acquisition. Before the first lock, the transaction may perform non-locking identity validation and bounded allocation of candidate-generated IDs needed by its operation. ID allocation uses only non-locking generators, adds each ID and its actual namespace-6 tuple to the bounded plan, and passes that exact ID to its insert rather than relying on a later database default; no DML or lock is allowed during planning. The advisory rank is shared namespace 2 when switch admission applies → namespace 8 for the authenticated physical-base slot/barrier → exclusive per-scope namespace 7 → existing verifier-material bigint lock(s) when applicable (exact `hashtextextended(key_material, 17017)` identity, deduplicated and signed-bigint sorted; registration entry paths pre-acquire before verifier row/index work) → namespace 5 for sweep operations → namespace-6 global-ID locks → namespaces 3 and 4 in canonical actual-key order. The full acquisition sequence takes and validates the lifecycle row immediately after namespace 7 and before verifier-material or other ranked relation locks; this is the explicit early-row exception to the remaining schema-derived FK-SCC row order. A path that omits an earlier applicable gate must not acquire it later. Non-locking authoritative checks run against a fresh statement snapshot after the required gates. The kill-switch transition holds namespace 2 exclusively, then takes the exclusive scope fence in its private recovery path and proceeds to namespace 5 without reacquiring namespace 2; private physical-base recovery also takes namespace 8 before namespace 7. Namespace 1 remains last for event-chain serialization. No early check may call a row-locking lifecycle helper. A duplicate identical identity reads the same row; a reused call ID with any differing field fails closed. The transaction commits before COM is entered.

The accepted-call record binds a non-reusable service process instance, host boot/service identity, optional 1C session instance, scope, target, operation, epoch, payload digest, dispatch CAS identity, monotonic state, and evidence references. It is append-only or otherwise monotonic. Its uniqueness and all foreign-key scope bindings are database enforced. A local process cache is never the idempotency source of truth.

The physical COM boundary is base-wide, even when the ledger has multiple tenant/company scopes. The database has one authenticated `physical_base_slots` row per base fingerprint and permits only one unresolved dispatch CAS for that physical base. This is claimed in the same transaction as the S12 `record_call` `PERMITTED → DISPATCHED` CAS/event and the admission record; a second call in another scope is refused with `BASE_CALL_IN_PROGRESS` until the prior call reaches an evidence-backed terminal state. S12 `begin_apply` and permit issuance are earlier preparation steps and do not authorize COM; the S13 admission transaction is the sole dispatch CAS. The slot is not released on COM return, timeout, process exit, lease expiry, or a local mutex unlock. Only terminal routines that validate the complete S12 evidence set may release it. A dedicated namespace-8 base lock precedes namespace 7 in the lock rank; the row/partial-unique guard is the durable invariant, while the advisory lock only orders concurrent transactions.

The transaction boundary has three distinct stages. First, S12 claim-token consumption/`begin_apply` and the existing approval/signature path may commit the permit as `PERMITTED`; no COM invocation is possible at this stage. Second, the single top-level transaction behind `PostgresAdmissionStore.admit()` / `private_writer_admit_v1` validates the exact permit, performs the existing `record_call` CAS and `DISPATCHED` event, claims the physical-base slot, and inserts the immutable dispatch attempt atomically. It must not call `record_call` as a later separately committed adapter operation. If this transaction aborts, none of those effects may remain; if its acknowledgment is lost, the caller performs exact durable lookup and never invokes COM from an uncertain result. Third, `mark_invoking()` is a separate short top-level transaction that rechecks authority and commits the monotonic invocation-stage CAS. The COM method is awaited only after that commit returns `true`; a lost/uncertain acknowledgment is lookup/recovery-only and never triggers a second invocation. Each store operation ends its PostgreSQL transaction before the next stage, and no database transaction or row lock spans COM.

### Physical invocation and result

Only the process that wins durable admission may invoke COM, and only once. Before entry it persists an invocation-stage transition tied to its process instance. `mark_invoking` must acquire namespace 2 when required → namespace 8 → namespace 7, lock and validate the lifecycle row as the single early relation-row exception, then lock the serving and exact attempt rows and recheck the current serving epoch, lifecycle epoch, scope admission/barrier state, applicable kill-switch state, and ownership of the base-wide slot. A barrier or kill-switch change that wins first prevents COM entry; an invocation-stage transition that wins first is included in the barrier's unresolved set.

The COM adapter owns the final pre-entry authority check immediately before the mutating COM method: current entitlement, permit signature/expiry/revocation, relevant authority epoch, kill-switch, authenticated base fingerprint, target/pre-version, operation and generation. The initial coordinator checks are early rejection only. For `CREATE_DRAFT`, it must prove the canonical input payload digest equals the approved digest and that the exact mapped COM field/line assignments derive from that payload; caller-added or altered fields are rejected before entry. For `POST`/`UNPOST`, it must enforce the approved pre-version atomically with the operation or under the separately qualified serialization boundary in S12. If a final check refuses after the durable CAS, the adapter may return a signed `PRE_WRITE_NO_EFFECT` receipt only when a process-bound guard proves the mutating method was never entered; otherwise the outcome remains uncertain and holds the base slot. The call result and signed receipt are committed through the S12 evidence path. A process crash or communication error after the invocation may have started leaves an unresolved call; a subsequent process may query and reconcile it but may not call COM again.

Receipt classification is closed and fail-closed at the coordinator boundary. `CALL_RETURNED_SUCCESS` is eligible for successful outcome verification only when its signed record is bound to the exact attempt and records an entered/invoked stage plus `call_returned=true`. `PRE_WRITE_NO_EFFECT` is eligible for the no-entry terminal path only with `write_invocation_stage=NOT_INVOKED` and `call_returned=false`, followed by the durable one-way guard transition that prevents later COM entry. `CONDITIONAL_VERSION_CONFLICT` is eligible for conflict recovery only when the mutating method was entered and returned; it requires the exact signed S12 receipt, completion, supervisor challenge and challenged outcome set, the structural conditional-conflict validator, and the database's inherited T16 signer/hold checks under the current serving epoch. Every other result-class/stage/return combination remains `POSSIBLY_EXECUTING`/unknown, preserves the base slot, and cannot authorize retry. The current coordinator exposes these routes, but concrete receipt/evidence resolvers and the validating database routines are not installed or qualified.

The outcome API returns a closed typed status such as `NOT_ACCEPTED`, `ACCEPTED_NOT_INVOKED`, `POSSIBLY_EXECUTING`, or `TERMINAL_WITH_EVIDENCE`, with the immutable call tuple and evidence reference. It returns no caller-controlled “success” flag. `ACCEPTED_NOT_INVOKED` is terminal only when a durable process-bound guard proves the mutating COM method was never entered. Terminal effect claims additionally require the S12 receipt, independent verification, and any required completion proof.

### Quiescence barrier

`fence_scope(scope, expected_current_epoch, barrier_id)` is idempotent by `barrier_id`. Its linearization point is the transaction that takes the namespace-8 physical-base guard before the exclusive namespace-7 scope fence, compares the current lifecycle epoch, computes the next epoch in PostgreSQL, temporarily closes admission for the authenticated physical base, and snapshots every unresolved call for that base across all scopes. The returned database epoch is authoritative and is used in the physical acknowledgement. Calls submitted later with an old scope epoch or during the base barrier are rejected. Calls already admitted remain owned and are not cancelled by the barrier. The database closure commits before the coordinator waits for the local COM queue; a local drain timeout leaves the immutable barrier durably closed for later resume.

The service waits only within an explicit bounded request deadline for eligible calls to become terminal. It then obtains a signed physical-writer quiescence acknowledgement from the COM-bound writer port after that port has closed its local per-base dispatch queue and serialized behind any current call. The acknowledgement binds the exact base fingerprint, scope, lifecycle epoch, immutable `barrier_origin_instance_id` / `barrier_origin_service_epoch`, barrier ID, and ordered complete base-wide call set; the coordinator verifies it against a distinct trusted barrier-signing identity before the DB can finalize the barrier. On restart, replay must return the exact signed acknowledgement for that stored origin. The current serving instance/epoch is checked separately by the database finalization routine and is not substituted into the historical acknowledgement. The response identifies the epoch, barrier, and complete pre-barrier accepted-call set; it never omits a call because of pagination or a local cache. If the result set is too large, the journal or writer is unavailable, the acknowledgement is missing/mismatched, or any call remains queued/in flight/unknown, return a non-ready result and retain the base and scope holds. A timeout does not make a call terminal. Repeating the same barrier ID returns the same durable barrier record and monotonic progress. After valid finalization the temporary base-wide close may clear, while the requested scope remains closed at its advanced epoch.

The coordinator's request wait uses a five-second default and a 30-second source maximum; smaller positive values may be supplied, but the validated setting is immutable after construction. This is only the caller's wait bound. A timed-out or cancelled caller does not cancel the retained physical-close task or release its serving-authority mutex; the task keeps that mutex until queue closure actually completes. This service wait is separate from the five-second PostgreSQL transaction deadline. The 30-second maximum is a candidate bound and must be exercised at and above the boundary, including cancellation and retained-task behavior, before any listener is enabled; it is not a measured latency or an operational qualification.

### Persistence and restart

PostgreSQL is authoritative for scope epochs, accepted call identities, barrier records, and durable state/evidence references. COM work occurs outside database transactions. Before a listener or dispatch path is enabled, a new process atomically claims a monotonically increasing exclusive serving epoch and obtains the complete durable snapshot of unresolved calls and open barriers in the same startup transaction. The epoch fences any prior process from new admission and from winning `mark_invoking`; it does not cancel an invocation whose `mark_invoking` CAS already committed. That in-flight call is inventoried as `POSSIBLY_EXECUTING` and retains the hold. Admission and invocation-stage CAS compare the caller's service instance with the current serving epoch, so a superseded process cannot enter COM. Missing, malformed, partial, or unavailable state keeps admission closed. The snapshot must discover a barrier whose close committed but whose response was lost; restart must not depend on volatile caller memory retaining the `barrier_id`.

A new process never invokes a call admitted by an earlier process. An orphan in `ACCEPTED_NOT_INVOKED` can become terminal only through store-validated S12 `PRE_WRITE_NO_EFFECT` receipt evidence tied to the original dispatch CAS and process-bound invocation guard. The proof transition and the old owner's `mark_invoking` transition must be one atomic compare-and-set race: if invocation wins, recovery refuses; if recovery wins, the old owner can no longer enter COM. An orphan in `POSSIBLY_EXECUTING` can become terminal only through store-validated `OutcomeEvidence` plus the matching S12 `CompletionProof`; neither a caller result nor an outcome observation alone authorizes terminality. For an entered `CONDITIONAL_VERSION_CONFLICT`, the store must also verify the already durable T16 operator and recovery-witness signatures and all role-independence rules before committing `FAILED_APPLY` or releasing any hold/reservation; evidence references alone are insufficient. These recovery writes are append-only, exact-attempt-bound, and never call COM. Without the required evidence, the call and scope remain held and `NOT_READY`.

The coordinator exposes startup inventory inspection while dispatch remains closed. The adapter binds its result to the exact process instance and newly claimed serving epoch. Recovery callers can use that complete view to reconcile an exact call or barrier after a lost response. `prepare_to_serve()` is a separate operation: it enables dispatch only when the database adapter returns the matching process/epoch, a complete readiness reference and no unresolved calls or open barriers. The adapter must validate S12 evidence and the readiness preconditions; an opaque string, empty/partial inventory, caller assertion, stale service epoch, timeout, or service-local cache cannot establish readiness.

PostgreSQL state remains authoritative through restart. PID, task state, connection close, and process death alone do not prove that the 1C operation stopped or had no effect. No lease-expiry shortcut may clear a hold.

## Lock, grant, and migration constraints

The 2026-10-22 source-final inventory (`S13_SOURCE_FINAL_GRANT_AND_LOCK_INVENTORY_2026-10-22.md`) identifies that source grants are not effective installed-grant evidence and reports an event-trigger order in which `events_chain` can acquire the chain advisory lock before the lifecycle row lock. It also finds that lifecycle triggers/API coverage do not establish one shared fence across all mutations, permits, and physical dispatch.

The durable S12 dispatch-attempt and S13 barrier schema proposal is in `S13_POSTGRES_ADMISSION_SCHEMA_DESIGN_2026-10-22.md`. It preserves `PERMITTED → DISPATCHED` as the single authorization CAS and remains a design proposal; no additive migration or durable adapter is implemented.

Therefore:

- Do not activate migrations 022–024 or treat `lifecycle_writer_epoch()` as a physical writer fence.
- Do not add a migration or `READY` transition until the full mutator, grant, trigger, row/advisory lock, unique-conflict arbitration, and writer-entrypoint map has a reviewed common ordering and every path participates.
- Preserve the event-chain lock as the last named lock; no path may wait for a row or scope fence while holding it. Reconcile the current trigger ordering before defining the additive migration.
- Keep the new service unavailable to application/read roles. Effective installed PostgreSQL grants must be read and recorded on the disposable database after migration qualification; source `GRANT` statements alone are not evidence.
- Keep five-second bounded lock acquisition/restoration behavior from migrations 023–024 when designing later additive paths; any changed bound or order requires explicit reliability review.

The current local disposable PostgreSQL instance was inspected read-only by the database-reviewer: it has no `change_ledger` schema, no matching grants or functions, and the connected admin role is highly privileged. This is source-independent evidence about that instance only; it does not establish grants on Ivan's host or any production database. No migration was applied for this design.

### Selected common-order and barrier protocol (design proposal; local candidate code exists, runtime not qualified)

The current worktree contains a candidate `PrivateWriterService`, `PostgresAdmissionStore`, and lazy Windows COM STA lane in `src/erp_mcp_private_writer/`. This establishes local source presence only: the adapter calls the candidate v1 database routines, which were absent from the inspected disposable `business_ai` catalog, and the guarded clone's COM connection has not succeeded. The implementation is therefore not database-integrated or physically qualified; do not describe the writer boundary as operational.

The historical direction in this document was a shared per-scope transaction fence for ordinary mutations and exclusive acquisition for recovery. The current conservative candidate supersedes it: every mutation and recovery transaction takes the same exclusive per-scope advisory fence because the full pairwise lock graph and same-scope unique-conflict ordering are not yet proven. The previous PM Bridge review `875580c2-0610-452c-bf74-678f455bf59e` / `cecff738-6524-4a08-8636-7c48575aaef5` reviewed the shared candidate and does not approve this changed concurrency contract. Do not implement the earlier serial-singleton-mutex proposal or its global `MUTATION_BUSY` behavior. The current exclusive-fence candidate and canonical order are in `S13_SCOPE_FENCE_IMPLEMENTATION_DESIGN_2026-10-22.md`; exact-hash review remains required before migration preparation.

The exact database lock contract is in `S13_SCOPE_FENCE_IMPLEMENTATION_DESIGN_2026-10-22.md`. Existing namespace 5 remains reserved for recovery sweeps; namespace 6 carries global caller-ID keys; namespace 7 is the exclusive scope fence; and namespace 8 is the authenticated physical-base slot/barrier guard. Private-writer paths use namespace 2 (when required) → 8 → 7 → lifecycle row (single early relation-row exception) → verifier-key locks → 5/6 → 3/4 → remaining schema-derived FK-SCC rows → 1. The namespace-2 shared key exactly matches the existing exclusive kill-switch resource, so switch disablement and effect admission serialize without a `7 → 2` cycle. Public sweep paths retain their compatible namespace-2 → 7 → lifecycle row → 5 order; the kill-switch helper does not reacquire namespace 2. `call_id` is consumed globally at the first committed dispatch CAS. A private-writer transaction has a five-second total deadline plus the separate bounded advisory-fence budget; all errors roll back and retain an unknown outcome where commit/invocation certainty is absent. These are design requirements only; the source map and runtime still need exact review and disposable qualification.

The source-final inventory must prove coverage for every runtime-granted mutator, delegated helper, trigger-mediated write, recovery stage, kill-switch path, direct-DML route, and unique-conflict arbitration point. A per-scope fence alone does not serialize concurrent mutators with each other and does not order a global unique-index conflict across different scopes. Namespace 6 must cover every global primary-key and contract identity domain enumerated in `S13_SCOPE_FENCE_IMPLEMENTATION_DESIGN_2026-10-22.md`, with table-specific keys for generated UUIDs and caller-selected IDs. Candidate-generated IDs are allocated before the first ranked lock and included in the bounded lock plan; a top-level transaction spanning more than one `(tenant_id, company_id)` scope is rejected before locking until a separately reviewed batch protocol exists. Dependent unique conflicts and sweep counters/failures reuse the matching domain key. Exact key encodings, collision-aware integer ordering/deduplication, and namespace rank are specified in the scope-fence design. The new S13 schema must separately define `dispatch_attempts.call_id UUID NOT NULL UNIQUE` because the current dispatch-permit schema has no unique constraint on that field; `NOT NULL` prevents ordinary PostgreSQL unique semantics from allowing repeated nulls. The source-wide proof must include `validate` business-key ordering, event-trigger/lifecycle ordering, verifier-key locks, recovery/kill-switch locks, and every `ON CONFLICT` target. Keep the event-chain advisory lock last; no path may wait on a row or another fence while holding it. No migration is authorized until database and reliability review accept the complete path map.

Fence acquisition uses a bounded wait and a stable refusal mapping. On timeout or SQL error, the operation aborts and the service rolls back and discards its fresh top-level transaction; it never catches the error in a savepoint and continues. No failure clears admission/barrier holds or fabricates an outcome. Revoke bypass DML and verify installed privileges; a statement trigger may be defense in depth but cannot repair an API that takes locks before entering the fence. No public/read role receives mutation authority. Owner/admin maintenance is a separate quiesced operation.

For linearizable quiescence, the database admission state is authoritative and participates in the base/scope fence order. Admission claims the one-per-base unresolved slot atomically with the S12 dispatch CAS. Barrier close blocks all new admissions for that base, advances the requested scope epoch, and captures every unresolved base call across scopes. After a registered-key signed physical-writer acknowledgement covers that exact call set and all calls have terminal evidence, finalization reopens other scopes but keeps the requested scope closed. `CLOSED_WITH_HOLD` is not quiescence and never advances readiness. COM runs outside PostgreSQL transactions. On restart, the service reads the durable base slot, barriers, and unresolved calls before accepting traffic; uncertainty fails closed. A service-local journal may accelerate recovery but cannot override database admission or outcome state.

## Independent design review

An actual architecture review found no contradiction between this design and the operator's writer decision or the inherited S12 contract. Read-only database review confirmed that there is no safe table/trigger-only fence addition on the current source. Follow-up review requires the common-order proof to include `recover_sweep`/`revoke_stale`/`kill_switch` advisory and row-lock chains plus unique-index conflict arbitration, in addition to event-chain, lifecycle, business-key, verifier-key, and granted-API paths. A forward migration may preserve migrations 022–024 unchanged, but must replace or wrap the relevant granted APIs and trigger paths, establish the complete source-wide lock order, and align the database epoch with the private service's durable admission/barrier. These source obligations are documented in the review evidence and must be closed before designing an activating migration. Until then, migration 023's recovery refusal and lifecycle `NOT_READY` remain in force.

A focused read-only database review of the namespace-2 source map found a possible `record → 2 → 5 → record` wait cycle if the shared switch lock were placed inside the late `assert_switch_off` helper. After the inventory and candidate scope design were amended to require the same shared advisory key at each participating API entry before row/conflict locks, the reviewer confirmed this finding resolved at the candidate-design level. It does not accept the full source-wide map, implement the gates, or qualify a migration.
The full static source-map reviews completed on 2026-10-23 by the database and reliability roles both conclude **NO-GO for additive-migration preparation**. The candidate rank is internally consistent, and the namespace-2 late-lock cycle is resolved in the candidate wording, but the source inventory does not yet close all affected-row discovery, trigger ordering, parent-before-child prelocks, or exact cross-path unique-conflict arbitration. The reviewer also confirmed the durable call-ID mechanism is the candidate global `dispatch_attempts.call_id UUID NOT NULL UNIQUE` constraint, inserted atomically with the S12 CAS; namespace 6 alone is not durable uniqueness. None of these candidate mechanisms exists in the inspected migrations. Keep recovery refused and lifecycle `NOT_READY` until the full map and implementation are complete.

The follow-up source inventory also identified that `recover_sweep` obtains its global `sweep_runs.run_id` only from the final INSERT default, after ranked locks and row work. The candidate contract now requires preallocating the exact ID before the first ranked lock, acquiring namespace 5 before namespace 6, preflighting the global primary key before row locks or recovery DML, and inserting the exact preallocated ID. The `kill_switch` OFF path must allocate before exclusive namespace 2 and pass that ID into a private helper without reacquiring namespace 2. This correction is recorded in the source inventory, disposable qualification case, and scope-fence design; it does not change SQL or lift the NO-GO.

## Adversarial review remediation proposal — 2026-10-23

This section supersedes the earlier per-scope-only physical exclusion and barrier prose above. It is a proposed response to GPT-PM full review `fce52676-2175-408b-85e1-35fb43e1e3a8`; the reviewer reply was routed to canonical project `erp_mcp` / repository `ERP_MCP` and returned `REVISE`. No runtime behavior or review closure is implied.

- **Base-wide physical-call exclusion:** one authenticated `physical_base_slots` row per base fingerprint limits the whole physical base to one unresolved dispatch CAS, across tenant/company scopes. Claim it atomically with S12 dispatch CAS and admission; only fully validated terminal S12 evidence may release it. A persistent `BASE_CALL_IN_PROGRESS` refusal is required for a competing call. Namespace 8 orders this base slot/barrier before namespace 7 scope fencing; database state, not an in-process mutex, remains authoritative.
- **Final invocation gate:** `mark_invoking` revalidates the current serving epoch, lifecycle epoch, scope admission/barrier state, kill-switch state, and ownership of the base slot in the same transaction. A barrier/disablement that wins first blocks COM; a transition that wins first is included in the complete barrier inventory.
- **COM-entry ownership:** the actual writer-port method owns the final entitlement, permit signature/expiry/revocation, authority-epoch, kill-switch, base-fingerprint, target/pre-version, operation, generation, and payload-digest check immediately before the mutating COM method. For `CREATE_DRAFT`, canonical approved payload and exact COM field/line mapping must match. A post-CAS refusal is `PRE_WRITE_NO_EFFECT` only with a signed process-bound proof that COM was never entered; otherwise the call and base slot remain unresolved.
- **Physical barrier acknowledgement:** the database closes the base admission slot and requested scope, computes the next scope epoch, and snapshots all unresolved calls across that base. The COM-bound writer serializes its physical queue and returns the versioned `BarrierAcknowledgement`: signature domain `ERP_MCP_R2:S13:PHYSICAL-WRITER-BARRIER:v1\n`, UTF-8 canonical JSON with sorted keys, ASCII escaping, compact separators and non-finite numbers forbidden, key ID/version and `signed_at` exactly `YYYY-MM-DDTHH:MM:SS.ffffffZ`, base/scope/resulting epoch/barrier/call set, immutable barrier-origin instance/serving epoch, writer service/host/boot/process identity, independent process-attestation reference, monotonically increasing queue epoch, and `local_queue_closed=true`. Ed25519 signs the domain prefix followed by that canonical JSON body; the detached signature is 64 raw bytes. An independent trusted registry validates that exact key version was authorized and not revoked at `signed_at`, plus the host/process attestation; it never substitutes a newer key for an unknown version. The signed boolean alone does not prove that the queue is closed. Only matching acknowledgement plus complete terminal S12 evidence permits `QUIESCED`. A post-restart resume replays the original immutable origin tuple and returns the exact persisted signed acknowledgement for the inventoried barrier; the replacement's current service instance/epoch separately authorizes database finalization. The temporary base closure may then clear while the requested scope remains closed at its new epoch.
- **COM invocation context:** after the durable winning CAS, the coordinator passes a typed `InvocationContext` with CAS, service instance/epoch, host, full scope/call/operation/generation, target/pre-version, permit ID/digest, authority epoch, `digest_set_hash`, and the separately bound approved payload digest. The COM port must authenticate the process independently and consume a durable one-way, per-call entry guard immediately before the mutating method. No context field by itself grants authority. `FailureEvidence` cannot classify definite no-effect from a non-empty dictionary; only a registry-validated, process/CAS-bound S12 receipt plus a durable guard that makes later entry impossible can do so. The COM port returns original signed receipt bytes; trusted verification rejects duplicate JSON keys and noncanonical bytes before constructing any parsed envelope.
- **Successful terminal path:** writer return and receipt persistence leave the call unresolved and the physical-base slot held. A separate read-only outcome verifier must bind the exact receipt to independently observed `OutcomeEvidence` and `CompletionProof`; a dedicated database terminal routine then rechecks all immutable references and S12 equalities and atomically records success, consumes the call ID, and releases the slot. The entered conditional-conflict recovery routine remains separate and cannot be used to finalize success.
- **Error provenance:** the adapter exposes only closed, stable database failure codes and SQLSTATE class through a typed store-error contract. The coordinator preserves those codes without propagating driver text or secrets; ambiguous outcomes remain lookup-required and never authorize a retry. Unrecognized failures map to a generic fail-closed service error while retaining `UNKNOWN` transaction outcome.

The source now has a PostgreSQL adapter implementation, but it remains non-operational until the versioned schema/routines, effective grants, caller identity, and listener composition are implemented and qualified. The physical-base slot in that schema, authenticated barrier-ack verifier wiring, and COM implementation are still absent. The full granted-path/lock graph, exact-hash GPT-PM review of this amended proposal, disposable PostgreSQL evidence, S12/S13 functional/E2E qualification, and physical COM-clone qualification remain open.

## 2026-10-23 S13-R7 recovery-boundary remediation candidate

### Post-completion observation watermark (S13-R7-B01)

Entered conditional-conflict recovery requires `CompletionProof → PostCompletionChallenge → PostCompletionReadAttestation + OutcomeEvidenceV3`, not V2. The supervisor signs a random nonce and oracle query-plan digest after completion. A distinct, process-attested read-attestor signs the nonce-bound request digest, source-response digest, exact V3 observation-claim digest, and durable sequence above the challenge floor; V3 binds that attestation digest. Wall-clock comparison alone is not accepted. Same-host timestamps are an additional consistency check; cross-host timestamps are not an ordering oracle. The terminal database routine must independently resolve and recheck all immutable records, active serving epoch and causal bindings before `FAILED_APPLY` or hold release. No production read-attestor or persistent sequence implementation exists yet.

### Writer/verifier identity separation (S13-R7-M01)

The immutable trusted identity snapshot rejects any service ID that appears under both `writer_receipt` and `verification_worker`, even when the keys differ. Every terminal record-set check still verifies each record against its exact registered role/service/host and scope. Independent key material alone does not satisfy service separation.

### Receipt recovery after lost persistence (S13-R7-M02)

`OneCWritePort.lookup_receipt` is read-only and keyed by the complete immutable call identity plus the winning dispatch CAS. It returns either the original canonical signed receipt bytes or `OUTCOME_UNRESOLVED`. Missing/unavailable storage is never proof of no effect. Recovery validates the bytes through the trusted writer-receipt verifier, idempotently attaches the exact receipt reference to the original `POSSIBLY_EXECUTING` attempt, then follows the existing success-verification path. It never invokes COM again. Conflicting bytes, missing receipt, verifier failure, persistence ambiguity, or lookup uncertainty keep the attempt and base slot held. The SQL attach operation must compare the full tuple/CAS and allow only an absent reference or the same immutable digest.

### Serving-epoch ownership for barrier mutation (S13-R7-M03)

Both `close_and_advance` and `finish_barrier` carry `service_instance_id` and `service_epoch`. Their SQL transactions acquire namespace 8 and namespace 7, lock and validate the matching lifecycle row, then lock and compare the active serving row before barrier mutation. A stale process cannot initiate a new barrier or finalize one after takeover. The current serving process may resume only an inventoried immutable barrier using its own active epoch; a stale replay cannot create a new barrier. The caller-side adapter has been updated to pass these values, but the SQL routines remain absent and this interface change is not runtime-verified.

### Follow-up constraints from the independent S13-R7 recheck — 2026-10-23

- The durable call snapshot must retain the original `owner_instance_id` for a `POSSIBLY_EXECUTING` call. Receipt verification binds to this original owner/process, never the recovering process. A distinct `attach_recovered_receipt` database operation carries both the active recovery service instance/epoch and the original owner; it verifies the complete immutable call/CAS tuple and accepts only null→same receipt digest or same-digest replay. It cannot release the hold or rewrite the original process identity.
- A `PRE_WRITE_NO_EFFECT` receipt recovered by physical lookup is routed through the existing atomic `record_recovered_not_invoked` transition, which must validate the durable one-way process-bound no-entry guard and prevent later COM entry. Receipt lookup/missing receipt alone still proves nothing. Unknown lookup and conflicting receipt bytes remain unresolved and held.
- A stale service process may replay a closed barrier before the database `finish_barrier` call. The licensed lane is therefore single-host unless a cross-host fencing primitive is separately qualified. On that host, startup epoch takeover and physical queue closure must acquire one ACL-restricted machine-wide serving-authority mutex before touching the durable serving epoch or queue. `quiesce` takes this authority mutex, then the exclusive physical-queue control, re-reads the serving epoch, and only then closes COM admission. Startup takeover uses the same outer mutex while advancing the database epoch. Thus takeover and close have one linearization order: a close that wins finishes before takeover; a takeover that wins makes the old caller fail before queue mutation. No database transaction spans COM. The physical close is idempotent by the complete base/scope/lifecycle-epoch/barrier/origin-instance/origin-service-epoch/call-set tuple. The database records the barrier origin on first close and never changes it on replay. A replacement coordinator replays that immutable origin tuple and receives the exact persisted signed physical acknowledgement; it does not re-sign under its new serving identity. Its current serving identity authorizes `finish_barrier` separately, and PostgreSQL verifies both current ownership and acknowledgement-to-origin equality. Thus a former process's acknowledgement proves only the historical physical close and gives that process no finalization authority. A conflicting barrier stays fail-closed until recovery resolves the previous close. The awaitable retains the host lease until the actual queue close has stopped admitting calls, including when COM work uses another thread.
- The `OneCWritePort` remains a non-operational skeleton; the host-wide mutex, ACL/ownership, lock order, and startup integration are design requirements, not runtime-proven behavior. If writer serving expands to multiple hosts, the local named mutex is insufficient and a shared distributed fencing primitive must be qualified before enabling that topology.
- `src/erp_mcp_private_writer/com_sta_lane.py` is a source-only COM STA queue primitive. It confines the injected COM connection and operations to one worker thread, admits one call at a time, keeps an accepted call alive across caller cancellation, requests worker cleanup if startup is cancelled, and closes local admission before draining. It allows only exact primitive results or bounded tuples across the thread boundary (16,384 visited nodes and a 2 MiB cumulative scalar budget), rejecting COM proxies and custom objects; floating-point results must be finite so NaN/infinity cannot cross into evidence serialization. `windows_com_lane.py` lazily creates `V83.COMConnector` in that worker and refuses to expose the session unless an injected read-only fingerprint measurement matches the configured SHA-256. Neither module is a `OneCWritePort` or listener integration; neither authorizes calls, produces trusted receipts, attests physical completion, or satisfies the S12/S13 queue barrier. Windows apartment/connector lifecycle and failure behavior remain `NOT_RUN` pending the authorized functional/E2E qualification phase.
- For entered conditional conflicts, recovery persists and validates `CompletionProof → PostCompletionChallenge → PostCompletionReadAttestation + OutcomeEvidenceV3`. The supervisor binds a random nonce and immutable oracle query plan to the attempt after completion. A distinct measured read-attestor binds the actual nonce-bearing request, returned response digest, exact outcome claims and durable sequence to one process-attested record. PostgreSQL atomically rechecks current serving instance/epoch, every immutable evidence reference, T16 signatures and hold release. This remains candidate-only: there is no deployed challenge issuer/read-attestor, sequence store, S13 SQL, or qualification result.

### 2026-10-23 source-path tightening — serving-authority mutex

The coordinator now requires an injected `ServingAuthorityMutex` before startup recovery or physical barrier acknowledgement can proceed. Both startup takeover and physical quiescence call `try_acquire()`, which must atomically return a lease immediately or return `None` without registering a waiter. `None` means ordinary contention and returns `SERVING_AUTHORITY_BUSY`; any exception from startup or quiesce acquisition or lease release latches `restart_required` and closes readiness because ownership may be uncertain. Startup fails closed with `SERVING_AUTHORITY_BUSY` if another process owns the mutex; after acquisition it asserts the lease, performs bounded epoch takeover, and releases the lease in `finally`. The only coordinator `quiesce` path starts a retained task that attempts the same non-queued acquisition and passes its live lease to the physical port. The request waits with a bound through `asyncio.shield`; timeout or caller cancellation does not cancel a task that acquired the lease or release that lease, and the task retains authority until the port call returns. A port error or cancellation of the retained task provides no proof that a worker-thread queue close stopped, so the service deliberately leaves the OS mutex owned, latches `restart_required`, and reports `ready == false`; a failed lease release after port success has the same fatal outcome. The listener must publish this readiness state and its supervisor must terminate that process before a new service instance can take over. A normal return is allowed only after the physical queue is closed, then the lease releases once. Retries of the same barrier join its active task within one service object; a second barrier is refused as busy while that task remains unresolved. `WindowsServingAuthorityMutex` now provides a source implementation using a physical-base-derived global mutex name and a security descriptor whose owner is the configured service SID and whose protected DACL grants only `SYNCHRONIZE`, `MUTEX_MODIFY_STATE`, and `READ_CONTROL` to LocalSystem and that SID. It accepts only the same canonical lower-case 64-character SHA-256 base fingerprint required by the lazy Windows COM connector, so alternate textual encodings of one physical-base identity cannot derive separate mutex names. It reads back and compares the named object's owner and DACL, failing closed if a pre-existing object has broader or different access; if that validation fails, handle cleanup is attempted and a `CloseHandle` failure must also be surfaced. Before any named-object API call, construction also requires the configured service SID to be the current token user or an enabled, non-deny-only token group; a missing identity or token query/cleanup failure refuses startup. Because Windows grants the owner implicit DACL control, the configured service SID is itself a trust boundary and must be exclusive to the trusted writer process. The mutex remains unwired to a listener or runtime SID configuration, and its Windows behavior has not been qualified. A missing mutex fails closed. Its cross-process acquisition must remain atomic and zero-wait; a blocking implementation would violate the no-waiter invariant. No concrete COM port or database routine is wired, so takeover-versus-close ordering remains **NOT_RUNTIME_PROVEN** and S13 is not qualified.

### Terminal recovery latch-race correction — S13-TA-M01 — 2026-10-23

The coordinator now uses one process-local async lock to serialize fatal `restart_required` latching with each terminal/recovery database call and recovered-receipt attachment. Each store call reacquires the lock after asynchronous evidence lookup, then rechecks the current active instance/epoch and, for restart recovery, exact startup-inventory membership. If the latch acquires the lock first, the store call is refused; if a bounded store call acquires it first, the adapter reaches its return/cleanup boundary before the fatal latch becomes visible. An indeterminate commit remains unknown and requires authoritative lookup; it is not upgraded to a successful commit by this lock. Cancellation while setting the fatal latch is shielded until the latch completes. This establishes only an in-process authorization ordering; SQL must still fence the durable active serving row and exact attempt through commit, and this source path has not been tested or qualified against a database.

The same remediation corrects the reachable qualification states: a live `PRE_WRITE_NO_EFFECT` result follows committed `mark_invoking` and therefore starts from `POSSIBLY_EXECUTING`; `ACCEPTED_NOT_INVOKED` remains a separate startup-inventoried recovery case. The stale-takeover case now includes `record_recovered_terminal`, and a dedicated race case must prove the latch-first ordering preserves the unresolved call, hold and physical-base slot. Recovered no-entry terminalization maps cancellation to `RECOVERY_TERMINALIZATION_UNKNOWN` with `outcome_unknown=true`; callers must perform authoritative lookup before any retry or follow-up action.

### Writer-receipt evidence registration candidate — 2026-10-25

Added `PostgresWriterReceiptRegistrar` as a source candidate implementing the existing `WriterReceiptVerifier` contract for S12 dispatch receipts and signed no-entry receipts. It parses through the production verifier's bounded canonical parser, loads the exact dispatch attempt from the evidence-ingest lookup, compares the full caller identity/process/CAS and database payload/repair bindings, verifies the unchanged original envelope against a fresh trust snapshot, then registers a typed projection through the narrowly granted SQL routine. The SQL write uses its own bounded `READ COMMITTED` transaction; it does not span trust lookup or any COM operation, and it does not terminalize or release a call. Evidence references are deterministic from record type and canonical record digest. Replays return the prior reference when the exact signed bytes and immutable business binding match; the first validator build ID remains provenance but is not part of replay identity, so a service upgrade does not change receipt identity.
