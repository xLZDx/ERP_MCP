## Current and retained implementation

- Current `promotion.py` checks attestation identity, approval, expiry, revocation, reviewer independence, and the expected head version before calling `promote_head`. `ports.evidence_digest` binds a revision digest and evidence reference; it does not hash the bytes at the reference.
- Retained commit `adc5ec7` adds a PostgreSQL port and Admin API wiring. The API retrieves the observed revision digest from SQL and passes it with the evidence reference. That design still needs an independently authenticated binding to immutable artifact bytes. Preserve the historical patch for comparison without importing its API, role provisioning, or settings wholesale.
- `artifact_vault.py` hashes bytes on insertion and provides scoped, access-checked `verify_evidence` against the stored digest. Verification does not hash content again on read. A provider adapter must hash the retrieved bytes, or prove an equivalent immutable read guarantee, before it can satisfy this contract.

## Proposed contract

1. Resolve the caller from authenticated context and authorize the exact tenant, source, and company before resolving any evidence. A trusted resolver maps the scoped revision and attestation to an immutable artifact version and its expected content digest. Caller-supplied references are lookup keys only.
2. Verify the bytes of the scoped immutable version against the trusted digest. Missing, revoked, ambiguous, mismatched, inaccessible, or unavailable evidence must stop a new promotion before its write call. Keep the revision/reference digest check as a separate invariant.
3. Choose one transaction authority for promotion eligibility. The bounded design pins a content-addressed artifact version and digest in a durable eligibility record. Register it only after authenticated byte verification and confirmation that the version cannot be changed, removed, or revoked independently of that record during use. Promotion and eligibility revocation must take the same scope lock, and promotion must recheck the eligibility record under the lock before updating the head. The existing SQL attestation and source-lock checks do not cover a separate provider's revocation. A provider whose pinning or revocation semantics cannot satisfy this contract is ineligible for durable promotion.
4. Persist a versioned canonical fingerprint with the scoped acceptance ID in the same transaction as the head update. It includes tenant, source, company, model, operation, requested rollback version when applicable, expected head version, target revision, authenticated requester and approver, attestation ID, evidence reference, immutable artifact version and content digest. Exact replay returns the original outcome. A changed fingerprint with the same acceptance ID is refused. Recovery uses authorized read-back of the durable fingerprint and outcome; an unknown result must not dispatch another write until it is reconciled. Preserve historical entries without a fingerprint as historical records; they cannot prove replay under this contract.
5. Keep this internal model operation separate from the read-only 1C data plane. No new public route is required for the bounded contract.

| Criterion | Observable behavior |

If eligibility revocation wins the scope lock after byte verification and before promotion, promotion refuses without changing the head. |
| TC047 | Two concurrent approvals with one expected version produce one accepted head and one conflict. Exact replay returns the original result; a changed request with the same acceptance ID is refused. |
| TC048 | Rollback to an incompatible or unauthorized target causes zero writes. Losing the response after commit does not create a second acceptance. |

First implementation slice: an internal verifier with a scoped reference and digest contract, integrated before the write boundary in an offline adapter. A durable eligibility record, acceptance fingerprint persistence, a qualifying provider, an authenticated production caller, and runtime qualification require their own evidence. Existing test and review receipts are historical until mapped to the chosen implementation.

## Durable SQL candidate

The existing `living.acceptance_events` key is `(tenant_id, source_id, acceptance_id)`, and its trigger makes events append-only. Keep that key for both old and new operations. Do not add company to the uniqueness key: changing company on a repeat must yield a mismatch, not a second acceptance. Current `promote_head` compares the model, expected version, target revision, approver role and evidence reference. Those columns cannot establish the new fingerprint, and old rows must not be backfilled from caller assertions.

The proposed companion acceptance record has the same key and a foreign key to the event. It stores fingerprint format, canonical request digest, and the verified eligibility reference. Only the restricted transaction entry point can insert it. Insert it in the same transaction as the existing head update and event. A missing companion for an existing event returns `HISTORICAL_EVENT` through the new path and permits no write. Add both tables without rewriting old events. Default-deny direct privileges, enable and force row-level security, add explicit scoped read policies for authorized read-back, and permit mutations only through restricted functions with separate verifier, operator, and promoter duties. Test the actual grants and policies, including calls made through older clients.

The model states are unenrolled, enrolled, and paused. Only unenrolled models can use the legacy write contract. Every reachable legacy SQL entry point, including direct `living.promote_head` calls, must check enrolment under the source lock before any replay or compare-and-swap. Enrolment and transitions to paused take the same lock. Neither paused nor enrolled may transition back to unenrolled as a recovery path. Registration and enrolment use the same authorization and locking boundary as promotion, even when old and new callers overlap.

Eligibility has a scoped opaque ID and binds exact tenant, source, company, attestation and revision IDs, artifact version, content SHA-256, and a recorded eligibility state. Registration is restricted to the trusted verifier. Registration, promotion and revocation take the existing source row lock before reading or changing eligibility. Lock order is source, eligibility, then accepted head. The transaction derives the approver database role with `living.caller_role()` and resolves it to the authenticated stable subject. The requester comes from a separately authenticated immutable request record, and the company must match the authorized database scope. An unavailable or ambiguous identity or company mapping fails closed. The transaction derives the fingerprint from validated fields. Neither a caller-provided digest of the request nor a caller-provided eligibility assertion is accepted as authority.

Freeze one canonical encoding and version before implementation. The encoding must preserve typed IDs and explicit null for a missing rollback version, distinguish operation kinds, and avoid delimiter ambiguity. Store an immutable exact digest with the event. For authorized recovery after a lost response, acquire the source lock and return one of exact committed result, conflicting use, historical event, or no commit. Timeout or inability to establish that serialization point returns unknown. Resolve that unknown before another dispatch. A conflicting use and a historical event both prevent another write for that acceptance ID.

Implementation order: define the canonical encoding and offline contract cases, establish the SQL transaction and negative authorization cases on a disposable database, then qualify a provider that can supply immutable bytes and honor the eligibility lifecycle. Qualification governs enabling the durable path. The pure encoding and disposable contract work can use synthetic authorities without making a provider claim.

### Fingerprint format candidate: `promotion-request-v1`

The digest input starts with the ASCII bytes `erp-mcp:promotion-request:v1` followed by one NUL. Fields follow in this fixed order: tenant, source, company, model, operation, requested rollback version, expected version, target revision, requester, approver, attestation, evidence reference, artifact version, content digest. The acceptance ID is the database key and is not part of the digest. Each nonnull field uses a `1` byte (ASCII), canonical decimal UTF-8 byte length, a colon, and exactly those bytes. Null uses the single ASCII `0` byte and is allowed only for the requested rollback version on promotion. Reject out-of-range integers and noncanonical identifier or digest representations before encoding. The operation is exactly `promote` or `rollback`, UUIDs are lowercase canonical text, and content digests are 64 lowercase hexadecimal characters. Use the exact authenticated and resolved string values rather than normalization performed by the encoder. Hash the framed bytes using SHA-256. Freeze golden byte vectors for null, multibyte text, delimiters inside strings, and the maximum signed database version before enabling more than one implementation.

Reference vectors, independently constructed from the framing rule. Both use tenant `t`, source `s`, company `c`, target UUID `00000000-0000-0000-0000-000000000001`, requester `u`, approver `v`, and attestation UUID `00000000-0000-0000-0000-000000000002`.

### Rollout and rollback

1. Expand on a disposable database with additive records and restricted entry points. Keep the fixture outside the normal migration directory and apply it only through an explicitly selected disposable test setup. Old consumers continue their existing behavior for unenrolled models. Existing acceptance events remain unchanged. Exercise an old client and a new client against the expanded schema, including a denied legacy write after enrolment.
2. Verify constraints and the lock order before enrolment. Confirm no companion record can exist without an acceptance event, no head change can commit without its companion in the new path, and direct writes by application roles are denied. Roll back an injected error between event and companion insertion to prove the head also rolls back.
3. Enable only an explicitly enrolled model with a qualifying provider. If promotion is paused or the provider fails, retain both records and reject new writes. Do not reopen the legacy write path for that model. A rollback of the deployment leaves enrolment enforced until a reviewed replacement can safely resume it. Defer contraction and any destructive schema change.
