# S13 scope-fence implementation design

Date: 2026-10-22. Status: implementation direction for source work; not migration approval, runtime qualification, or S13 acceptance.

## Goal

Establish one database ordering point between scoped mutators and recovery without holding a PostgreSQL transaction across checkpoint I/O or a COM call. Preserve the operator-selected private Ivan COM boundary and keep lifecycle `NOT_READY` until both database and physical-writer barriers are qualified.

## Constraints and current behavior

- The source-final inventory records conflicting paths: `validate(text,text,uuid)` locks a record before `A:key`; the event trigger sequence can request the chain advisory lock before the lifecycle row; named key-material advisory locks and unique-conflict arbitration also participate in ordering.
- The recovery entry point remains refused by migration 023. Existing source does not prove a global lock order.
- `change_ledger.assert_scope` is declared `STABLE` and is used by stable readers such as `amount_consumed` and the checkpoint-suffix reader. It must remain a scope assertion; adding an advisory lock there would make the stable contract misleading.
- The current disposable database has no `change_ledger` schema. Effective S13 grants are `NOT_VERIFIED` there.

## Options and decision

1. **Shared per-scope fence plus canonical internal lock order — selected.** It excludes recovery from all participating mutations while allowing compatible scoped operations to proceed concurrently. It is viable only if every mutating API and delegated mutation path acquires it first and all internal ordering conflicts are corrected.
2. **Exclusive per-scope fence for every API call.** This is a conservative fallback if source-wide ordering cannot be established, but serializes unrelated writes and readers within a tenant/company and adds unmeasured contention. It still does not fence COM after transaction commit.
3. **Manually place fences without one enforced entry point.** Rejected as the primary approach because omitted helpers, triggers, recovery stages, or future mutation paths can bypass it.

This selection follows the design review correlated to PM Bridge request `875580c2-0610-452c-bf74-678f455bf59e`, reply `cecff738-6524-4a08-8636-7c48575aaef5`. That review explicitly found a shared fence by itself insufficient: shared mutators can still reproduce a row/advisory inversion.

## Design

- Require `READ COMMITTED` for every top-level mutator and recovery transaction participating in the protocol. The adapter must make `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` its first SQL command after `BEGIN`; if the level cannot be set or observed as `read committed`, abort before acquiring a fence. This prevents a transaction snapshot taken before the fence from being reused for the post-fence checks. After acquiring the scope fence and any required namespace-2 kill-switch gate, each authoritative read is a new statement snapshot.
- Preserve existing advisory namespace 5 for the scope-specific sweep lock in migration 020. Reserve namespace 6 for global caller-ID keys and namespace 7 for the new scope fence. Add a dedicated `VOLATILE` mutation-fence primitive. Before the fence, perform only non-locking identity validation needed to derive the canonical scope/fence key. Encode the tuple without delimiter ambiguity as `octet_length(tenant_id)::text || ':' || tenant_id || ':' || octet_length(company_id)::text || ':' || company_id`, prefix it with `s13-scope:v1:`, and hash it with `hashtext` in advisory namespace 7. A 32-bit collision preserves fencing safety but can make recovery in one scope wait for a shared-lock mutation in another scope; it adds unnecessary delay, not a bypass. Acquire the per-scope transaction advisory lock in shared mode before any other advisory lock, row lock, or conflict-arbitrating write. After acquiring it, perform non-locking authoritative scope/lifecycle/epoch/admission checks against the fresh `READ COMMITTED` statement snapshot. These checks must not call a helper that takes a row lock. Then acquire the remaining advisory locks before any row lock; at the lifecycle row's assigned rank, lock it and recheck state/epoch before mutation. Recovery acquires the same scope key exclusively before changing recovery state or epoch.
- Do not add lock acquisition to `assert_scope`; stable read APIs remain outside the mutation-fence path. Enumerate every externally granted mutator, delegated leaf, trigger-mediated write, recovery stage, and kill-switch path, and prove each reaches the fence before any competing lock.
- Normalize post-fence ordering: namespace advisory locks in canonical order; claim-token rows; records in stable order; secondary rows; lifecycle row; event-chain advisory lock last. Rewrite the `validate` row-before-`A:key` path and correct event-trigger ordering. Include verifier-key locks and unique-index conflict paths in the source-wide map.
- A shared scope fence does not cover unique conflicts whose key omits tenant/company. The source-final inventory identifies caller-controlled global `records.change_id` (the original PK remains even after the later composite unique constraint); dependent conflict/key domains also carry or reference `change_id` in reservations, budgets, claim tokens, permits, business keys, evidence, receipts, and sweep counters/failures. `propose` is the record creator and takes the ID from its caller. `budget_admin` optionally accepts a caller `grant_id` and locks/creates that global PK. S12 also prohibits reusing `call_id` across generations or scopes, making it a global identity domain even though current permits lack a unique constraint on that field. Acquire per-key locks in advisory namespace 6, dedicated to global caller identities. Effectful mutators that check the kill switch take namespace 2 shared before reading its state; `kill_switch` takes namespace 2 exclusively. This makes switch-state validation atomic with effect admission. Preserve the current switch/recovery order: namespace 2 precedes namespace 5 (sweep), and namespace 5 precedes namespace 6 (caller IDs) on sweep paths. The public `recover_sweep` entry point takes the shared namespace-2 gate before namespace 5; `kill_switch`, already holding the exclusive gate, calls a private helper that assumes the gate is held and does not reacquire or upgrade it. Derive the two-integer key exactly as `(6, hashtext(domain_key))` using the existing `pg_advisory_xact_lock(namespace, hashtext(key))` convention in `take_lock`; `domain_key` is exactly one of `call-id:v1:`, `change-id:v1:`, or `grant-id:v1:` followed by the lowercase canonical 36-character UUID text (`uuid::text`). Record-subject counters/failures reuse the `change-id` key. A 32-bit collision is a shared advisory resource, not merely false contention: for a transaction requiring multiple keys, hash sorting can differ from lexical domain-key sorting. Therefore derive each actual two-integer lock tuple first, deduplicate equal tuples, then sort and acquire by the signed key integer ascending within namespace 6. Apply the same actual-lock-key ordering and deduplication to every multi-key acquisition within existing namespaces 2–5. The complete fixed rank is namespace 7 (scope fence), namespace 2 (kill-switch gate), namespace 5 (sweep), namespace 6 (global caller IDs), namespace 3 (hold), namespace 4 (business key), then row locks, and namespace 1 (event-chain) last. This reflects existing `kill_switch` → `recover_sweep` and recovery-helper order; it is intentionally not numeric order. Every path needing more than one of these namespaces must follow the same rank. Equal hashed lock tuples are acquired once. Hash collisions may make unrelated IDs contend, but cannot invert the order of resources acquired by any transaction that follows this rule. Scoped keys such as `(tenant_id, company_id, ...)` remain covered by the scope fence when every path participates. Generated surrogate UUIDs remain protected by their unique indexes and do not justify global serialization.
- Bound scope and global-ID advisory-fence waits to at most five seconds, preserving any shorter caller `lock_timeout` and restoring the prior setting after acquisition. A dedicated blocking-fence helper must catch only the lock-not-available condition raised by its own `lock_timeout`-bounded advisory-lock statement and rethrow the fixed contract code `LEDGER_LOCK_TIMEOUT` (`P0001`). It must not execute `NOWAIT` or unrelated lock operations inside that catch boundary. A raw SQLSTATE `55P03` elsewhere remains distinguishable as `SQL_55P03`; `57014` statement cancellation and `40P01` deadlock also remain fail-closed SQLSTATE-derived errors. Every failure aborts the fresh top-level transaction; no timeout or lock refusal may be caught by the adapter and followed by more SQL in the same transaction. This is separate from target/business-key `LOCK_BUSY` semantics.
- The database lock ends at transaction completion. The Ivan COM service must independently reject stale epochs, provide authoritative lookup by stable call ID, and complete a linearizable quiescence barrier before recovery can approach `READY`.

## Failure modes and rollback

- Missing fence on any granted path: that path is outside the recovery ordering proof; keep recovery refused.
- Shared fence acquired after a row/advisory lock: lock-order inversion remains; keep the migration unqualified.
- Fence timeout, database disconnect, or lost commit response: report an unknown/failed database operation with no retry of COM and no readiness transition.
- COM call unresolved after the database fence releases: keep the scope held and `NOT_READY`; only the physical boundary can resolve it.
- Rollback is forward-only: leave recovery disabled and dispatch fail-closed. Do not remove claims, clear holds, or replay physical calls as cleanup; do not edit migrations 022–024 in place.

## Rollout and verification plan

Implement an additive migration only after the full API/helper/trigger/conflict map is complete. Do not apply it during coding. After all in-scope code is complete, `functional-test-reviewer` and `e2e-runner` own mapped disposable-PostgreSQL scenarios for every mutator racing recovery; a barrier wait whose transaction snapshot predates fence acquisition; rejection of unsupported isolation; concurrent switch-state update versus effect admission; deliberately colliding namespace-6 and namespace-2–5 keys acquired in opposite logical-ID order; duplicate actual lock-key deduplication; lifecycle revalidation at the assigned row-lock rank; proof that the `kill_switch` wrapper does not reacquire/upgrade the switch gate while invoking recovery; fence timeout provenance versus unrelated `55P03`, statement cancellation `57014`, and deadlock `40P01`; full transaction rollback; direct grants; tenant/company scope; and dump/restore. Database, reliability, and security reviewers then review the exact tested head. The separately authorized COM-clone qualification must prove physical idempotency, stale-epoch rejection, outcome lookup, and quiescence; SQL evidence cannot substitute for it.

## Remaining dependencies and owners

- Accountable task owner: operator; local executor: Codex.
- SQL lock-order and effective-grant review: database-reviewer; the inspected disposable database lacks `change_ledger`, so S13 effective grants remain `NOT_VERIFIED` until a suitable disposable schema is prepared after coding.
- Required runtime proof: Ivan stack technical owner for the host/connection boundary; Codex implements the private service; no clone qualification has established the physical contract yet.
- `READY` remains prohibited until every SQL path and the independent COM barrier are qualified and all accepted calls have independently terminal evidence.
