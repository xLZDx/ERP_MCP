# S13 scope-fence implementation design

Date: 2026-10-22. Status: implementation direction for source work; not migration approval, runtime qualification, or S13 acceptance.

## Goal

Establish one database ordering point between scoped mutators and recovery without holding a PostgreSQL transaction across checkpoint I/O or a COM call. Preserve the operator-selected private Ivan COM boundary and keep lifecycle `NOT_READY` until both database and physical-writer barriers are qualified.

## Constraints and current behavior

- The source-final inventory records conflicting paths: `validate(text,text,uuid)` locks a record before `A:key`; the event trigger sequence can request the chain advisory lock before the lifecycle row; named key-material advisory locks and unique-conflict arbitration also participate in ordering.
- The recovery entry point remains refused by migration 023. Existing source does not prove a global lock order.
- `change_ledger.assert_scope` is declared `STABLE` and is used by stable readers such as `amount_consumed` and the checkpoint-suffix reader. It must remain a scope assertion; adding an advisory lock there would make the stable contract misleading.
- The current disposable database has no `change_ledger` schema. Effective S13 grants are `NOT_VERIFIED` there.

### Validator path crosswalk

Migrations 005 and 008 both show the historical `validate` shape, but 008 is the surviving
three-argument definition: it locks the `records` row `FOR UPDATE` at 008:297-299, reads the
`business_keys` row, and only then calls `take_lock('key', ...)` at 008:305-310. `lock_ns('key')`
maps that call to advisory namespace 4 at 008:1512-1522. The same transaction subsequently updates
business-key and record rows and appends the validation event; the event trigger takes namespace
1. This is concrete record-row → namespace-4 ordering, not evidence of a proven deadlock cycle by
itself.

The additive candidate must not preserve that order. After non-locking argument validation, the
fresh `READ COMMITTED` transaction acquires applicable namespace-2 switch admission and the
exclusive namespace-7 scope fence, then locks the lifecycle row as the documented early-row
exception. Under that serialization it reads the current record/business-key values to derive the
actual key tuple, acquires namespace 6 for the supplied global change ID and namespace 4 for the
business key before taking any remaining relation-row locks, then locks affected rows in the
approved FK-SCC order, updates lifecycle/business-key state, and lets the event chain take namespace
1 last. It revalidates that the key tuple used for locking is still current; a changed or
unavailable tuple aborts without mutation. This relies on every same-scope key/lifecycle mutator
using the exclusive scope fence; the source-wide caller map is still open, so it is a candidate
contract rather than proof about current migration behavior. Historical migrations remain
immutable.

### Unknown-outcome recovery crosswalk

The current `resolve_unknown_signed` wrapper reads the record/evidence before the leaf takes its
record lock (`007:552-592`, `507-550`). A retry/reset can then move the record through
`complete_lock_busy` to a later generation, reclaim it, and make it `APPLY_UNKNOWN` before the old
wrapper resolves its stale observation (`008:972-1004`; `009:492-493,570-574,674-681`;
`020:193-210`). The current wrapper/leaf chain therefore cannot use its pre-lock validation as
authority for later resource release.

The additive replacement must route the whole decision through one bounded top-level
`READ COMMITTED` transaction under the applicable namespace-2 and exclusive namespace-7 fences.
After taking the early lifecycle row, it reads the current record/attempt/evidence tuple to derive
the global namespace-6 keys, acquires those keys before remaining relation locks, and locks the
current record plus its exact dispatch-attempt/permit rows in the approved FK-SCC order. It then
revalidates the observation generation and call ID against the locked record, current attempt and
permit, and performs resolution or refusal without releasing any hold/resource from a stale tuple.
The versioned entry must not call the legacy wrapper/leaf after performing only unlocked checks.
This path depends on every retry, claim, dispatch and recovery writer in that scope using the same
fence; the current source-wide caller graph remains open. The disposable oracle is already
specified in `S12_S13_DISPOSABLE_QUALIFICATION_PREREQUISITES_2026-10-23.md` as a deterministic
generation-N versus generation-N+1 race. No historical migration changes are authorized by this
candidate text.

Cutover is additive and must not replace historical migrations. Source branches/effects: `007:507-550,552-592`; wrapper grant is recorded in `S13_SOURCE_FINAL_GRANT_AND_LOCK_INVENTORY_2026-10-22.md` source-final API table and grant inventory. ## Options and decision

1. **Shared per-scope fence plus canonical internal lock order.** Rejected for this candidate because it does not serialize same-scope mutators, while the complete pairwise lock graph and conflict-key coverage are not proved. It may be reconsidered only after source/runtime evidence shows all concurrent same-scope paths follow one deadlock-free order.
2. **Exclusive per-scope fence plus base-wide physical slot for private writer paths — selected as the conservative candidate.** Namespace 7 serializes database writes within one scope; namespace 8 and the durable slot additionally prevent multiple unresolved physical calls across scopes on the same base. The transaction still ends before COM, so persistent slot ownership and signed physical-barrier acknowledgement—not a held DB lock—preserve exclusion during I/O. Cross-scope/global identities still require namespace-6 locks and canonical ordering.
3. **Manually place fences without one enforced entry point.** Rejected as the primary approach because omitted helpers, triggers, recovery stages, or future mutation paths can bypass it.

The PM Bridge review correlated to request `875580c2-0610-452c-bf74-678f455bf59e`, reply `cecff738-6524-4a08-8636-7c48575aaef5`, is historical evidence for the earlier shared-fence candidate only. The exclusive-fence proposal changes the concurrency contract and does not inherit that approval; it requires exact-hash review before migration preparation.

## Design

- Require `READ COMMITTED` for every top-level mutator and recovery transaction participating in the protocol. The adapter must make `SET TRANSACTION ISOLATION LEVEL READ COMMITTED` its first SQL command after `BEGIN`; if the level cannot be set or observed as `read committed`, abort before acquiring a fence. This prevents a transaction snapshot taken before the fence from being reused for the post-fence checks. After acquiring namespace 2 when required, namespace 8 on private-writer paths, and namespace 7, each authoritative read is a new statement snapshot.
- Bound the entire fresh database transaction, including row locks, FK parent locks, unique/exclusion arbitration and commit, to a hard five-second ceiling measured from `BEGIN`; preserve any shorter caller deadline. After the required isolation command and before the first lock, initialize a monotonic adapter deadline and `SET LOCAL statement_timeout` to its remaining duration before each SQL statement. Bound commit by the remaining adapter deadline as well; a lost commit response is an unknown outcome. The five-second advisory-fence budget remains a separate cumulative bound within that outer deadline. Expiry aborts the transaction and yields a distinct `57014`/indeterminate outcome; no adapter may catch it and continue or treat it as evidence that COM was not entered. This is a conservative unmeasured design bound and must be reviewed against disposable-lane latency before enablement; it may only be raised by explicit reliability review backed by measurements.
- Preserve existing advisory namespace 5 for the scope-specific sweep lock in migration 020. Reserve namespace 6 for global caller-ID keys, namespace 7 for the new scope fence, and namespace 8 for the authenticated physical-base writer slot/barrier. For private-writer admission and barrier paths, the canonical advisory rank is **namespace 2 (kill-switch gate, when required) → namespace 8 (physical-base slot/barrier) → namespace 7 (exclusive scope fence) → existing verifier-key-material bigint lock(s) → namespace 5 (sweep, when required) → namespace 6 (global caller IDs) → namespace 3 (hold) → namespace 4 (business key) → row locks → namespace 1 (event chain)**. The full acquisition sequence has one explicit early-row exception: immediately after namespace 7, lock and validate the matching lifecycle row before verifier-material locks, namespaces 5/6/3/4, or any other relation row. Remaining relation locks follow the schema-derived FK-SCC order. Other effectful mutations that do not enter the private physical writer may omit namespace 8, but must never acquire it after namespace 7. This deliberately puts namespace 2 before 8 and 7: the existing `kill_switch` path holds its exclusive namespace-2 lock while entering recovery; requiring a writer to hold a later-ranked lock while waiting for namespace 2 would permit a cycle. Every effectful mutator that participates in switch admission must take namespace 2 shared before any later-ranked fence; recovery/public sweep takes namespace 2 shared before its later fences; the kill-switch path keeps namespace 2 exclusive and calls only a private recovery helper without reacquiring/upgrading 2. The private-writer base key is derived from the authenticated base fingerprint, prefixed `s13-base-writer:v1:`, hashed to `(8, hashtext(key))`; a collision only serializes unrelated bases. The scope tuple is encoded without delimiter ambiguity as `octet_length(tenant_id)::text || ':' || tenant_id || ':' || octet_length(company_id)::text || ':' || company_id`, prefixed with `s13-scope:v1:`, then hashed to `(7, hashtext(key))`. Before the first lock, perform non-locking identity/fingerprint validation and bounded allocation of every candidate-generated ID needed by the operation. ID allocation may call only non-locking generators; it must not acquire table/advisory locks or perform DML. Include each allocated ID and its actual namespace-6 lock tuple in the bounded plan, then pass that exact ID to its insert rather than relying on a later default. Namespace 8 serializes changes to the persistent one-owner-per-base slot and base-barrier state; a partial unique constraint is an additional guard. Namespace 7 is exclusive for each participating mutation/recovery transaction before row locks, unique/exclusion conflict arbitration, or other ranked locks. A 32-bit namespace-7 collision preserves fencing safety but may serialize unrelated scopes; it adds delay, not a bypass. Non-locking authoritative lifecycle/epoch/admission checks run after the applicable gates against fresh `READ COMMITTED` statement snapshots; they must not call a row-locking helper. The lifecycle row lock is separate from those non-locking checks and is held through commit to make later assertions stable. Row locks are acquired only for actual mutation targets and at their schema-derived FK-SCC ranks.
- The verifier-material lock is a pre-existing one-bigint compatibility lock, not an advisory namespace: retain `hashtextextended(key_material, 17017)` exactly, plan its actual signed bigint values, deduplicate and acquire a multi-key set in signed ascending order after namespace 7 and before namespace 5/6. For verifier registration/update, the trusted entry helper must pre-acquire all planned material keys before row/index work; `verifier_key_receipt_role_guard` may only re-acquire the `NEW` material key reentrantly. The current trigger does not establish this common rank for other callers, so the candidate requires audited entry coverage and fail-closed refusal for unenumerable key sets.
- After acquiring the namespace-7 gate, lock the matching lifecycle row as the single early relation-row exception. Perform authoritative lifecycle/epoch/admission reads in a separate fresh `READ COMMITTED` statement while retaining that row lock through commit; the read helper must not acquire another row lock. This preserves a fresh snapshot without allowing a lifecycle trigger or nested helper to wait for the row after later-ranked work has begun.
- The namespace-2 shared gate must use the exact existing `kill_switch` lock identity: `(2, hashtext(tenant_id || ':' || company_id))`, matching `take_lock('killswitch', t||':'||c)` in migration `008_change_hardening_b.sql`. Acquire it with `pg_advisory_xact_lock_shared` so it conflicts with the existing exclusive `pg_advisory_xact_lock` path. Do not replace the historical delimiter encoding in this compatibility lock; any collision only adds contention. The namespace-8 and namespace-7 keys use their separately versioned, unambiguous encodings above.
- Do not add lock acquisition to `assert_scope`; stable read APIs remain outside the mutation-fence path. Enumerate every externally granted mutator, delegated leaf, trigger-mediated write, recovery stage, and kill-switch path, and prove each reaches the fence before any competing lock.
- **Deterministic row-rank contract for the implementation:** derive the FK dependency graph from the exact installed additive schema, condense it into strongly connected components (SCCs), and order the acyclic component graph parent-component before child-component; order unrelated components by fully-qualified relation name. Do not impose a separate fixed `records`/`claim_tokens`/secondary-row order: the source DDL proves that `targets` is a parent of `records` (`records.base_fingerprint → targets`, `004:247`), `records` self-references through `parent_change_id` and `repair_for` (`004:222-223`, scoped constraints in `008:1865-1870`), and `records` is a parent of `claim_tokens` (`004:309-315`). Thus those components must order `targets → records SCC → claim_tokens` unless the exact additive schema introduces a cycle that places them together. For each cyclic SCC, discover the complete affected row closure after advisory pre-fences and lock all rows in the SCC by `(fully-qualified relation name, canonical primary-key tuple)` before any mutation in that SCC. For the existing `records` SCC, lock all involved parent and child records in ascending `(tenant_id, company_id, change_id)` order. Each key component is type-tagged and length-prefixed (UUIDs use lowercase `uuid::text`; text uses UTF-8 bytes). Deduplicate repeated keys before issuing locks. This rule applies to `FOR UPDATE`, `FOR NO KEY UPDATE`, `FOR SHARE`, and `FOR KEY SHARE`, including parent locks that referential checks would otherwise acquire implicitly. Before any `INSERT`/`UPDATE` that can wait on a unique or exclusion constraint, acquire the matching namespace-6 caller-ID lock for global keys or the scope fence for fully scoped keys; the source inventory lists each current conflict target. Multirow mutations must lock their complete key set in that order before mutating; a modifying statement's planner/heap order is not a lock-order guarantee. A trigger that takes any additional row/advisory lock participates in the same rank and may not introduce a back-edge.
- **Budget-grant parent plan:** `grants` is an FK parent of both `reservations` and `change_budget`, while `change_budget` also references `records` (`004:350-363`; `008:52-56`). For `claim` and `declare_budget`, derive and revalidate the grant/record/child key set with non-locking reads after the entry fences, acquire the grant's namespace-6 ID lock, then lock applicable `grants` rows before the complete `records` SCC and before `change_budget`/`reservations` child rows; insert/update only after this parent-first plan is complete. Both `grants` and `records` must precede `change_budget`; their relative order follows the candidate rule for unrelated components to use fully-qualified relation-name order (`grants` before `records`). This yields `grants → records SCC → child rows`, unlike the legacy source order (`records → grant/child`). Grant update/revoke paths lock only the grant parent; they must participate in the same scope/global-ID fence and row rank. If the grant state or planned child set changes between plan and locked revalidation, abort with `LOCK_PLAN_STALE` before DML. - **Complete lock-plan contract:** after namespace 2 (if required), private-writer paths take namespace 8 for the authenticated base slot/barrier, then the exclusive namespace-7 fence; other paths begin at namespace 7. Immediately after namespace 7, lock and validate the matching lifecycle row; this is the sole relation-row lock taken before verifier-material and namespace-5/6/3/4 locks. Derive a bounded operation plan from fresh non-locking reads. It must enumerate every intended row mutation, each applicable function/trigger write, all FK parent keys that would otherwise be implicitly locked, all globally shared conflict IDs, and every scoped unique/exclusion conflict target. Acquire each applicable existing verifier-material key first, then namespace 5 when required by a sweep path, namespace-6 IDs in actual signed-key order, then applicable namespaces 3–4 in their canonical rank. The current verifier lock identity is the exact signed bigint returned by `hashtextextended(key_material, 17017)` in `017_receipt_hardening.sql:38-54`; preserve this input and seed for compatibility. For every bounded plan, compute the actual bigint keys, deduplicate equal values, and acquire them in signed bigint ascending order. Trusted entry paths pre-acquire the complete planned verifier-material key set before verifier row/index work; the existing BEFORE trigger may re-acquire its `NEW.key_material` lock reentrantly. A path that cannot enumerate its complete material-key set before row/index work must refuse; only then acquire the complete remaining row-key set by the schema-derived SCC order and strongest required row-lock mode. Perform no DML while constructing/acquiring this plan. Re-read every branch predicate and the schema/migration contract fingerprint after all locks. If the actual write/trigger/key set differs from the plan, abort the fresh transaction with a stable `LOCK_PLAN_STALE` result before DML; any retry must begin a new top-level transaction and recompute the plan. Unknown schema fingerprints, unenumerated trigger effects, or an unbounded row closure fail closed. This is the implementation obligation that makes the SCC rule operational; the current source map has not demonstrated that every existing API can satisfy it.

## Failure modes and rollback

- Missing fence on any granted path: that path is outside the recovery ordering proof; keep recovery refused.
- Any required fence acquired after a row/advisory lock, or namespace 2 acquired after namespace 8 or 7: lock-order inversion remains; keep the migration unqualified.
- Fence timeout, database disconnect, or lost commit response: report an unknown/failed database operation with no retry of COM and no readiness transition.
- COM call unresolved after the database fence releases: keep the scope held and `NOT_READY`; only the physical boundary can resolve it.
- Rollback is forward-only: leave recovery disabled and dispatch fail-closed. Do not remove claims, clear holds, or replay physical calls as cleanup; do not edit migrations 022–024 in place.

### Candidate wait-for proof obligations — 2026-10-24

The candidate does not need a hand-authored total order for every pair of the 54 mutation names if the common entry protocol is complete. The proposed serialization argument is:

1. Each transaction is allowed exactly one top-level granted mutation/recovery entry, and that entry accepts exactly one authenticated `(tenant_id, company_id)` tuple. Before the first ranked lock, a database entry helper requires `READ COMMITTED`, requires `txid_current_if_assigned()` to be NULL (no earlier write or row-locking statement), and refuses any pre-held advisory lock or incompatible explicit relation lock on a `change_ledger` relation.
