Domain facts that drive the design (from the repo, not from this plan): the 818HA reference configuration has no accumulation register of settlements with counterparties among its 76 accumulation registers, and the published accounting-register record carries no counterparty sub-account fields (`core/DECISION_LOG.md`, entry "Real 1C 818HA L2 lane executed"). So a register-based `payable_balance` cannot be assumed; AP must be derived explicitly from an accounting-register (ledger) strategy or declared unavailable. `purchase_reconciliation.py` compares two listings only; nothing yet retrieves a listing page by page or proves what the listing is a listing of.

## Scope decision

S6b takes what can be built and tested offline over fixtures and fake ports, as unwired reference modules (new files only; the existing modules above are touched only for a defect proven by a failing test, same rule as S6 E3): US-031 as an AP strategy selector and a ledger-derived payable view, US-032 as a paginated posted-receipts retriever with a proof record and a three-way assessment. Everything that needs the real 1C read grant, a real paginated source, real MOLDRETAIL data, an accountant's attestation or real native report bytes stays NOT_RUN and operator-owned (listed below). The reserved capability `ap.account_based` in `validation_coverage.py` is NOT opened by this sprint: opening it needs PASS evidence on real data, so the name stays refused and the S6 E5 test (purchases-validated opens nothing for AP) stays valid. The modules expose a strategy and a retrieval result, never a capability flag.
