## Lock-order findings

Migration 008 states the intended order as named namespace advisory locks, claim-token rows, records, secondary rows, and the event-chain advisory lock last (`db/phase2/008_change_hardening_b.sql:3-15`). Static source review found these contradictions:

1. The historical `validate(text,text,uuid)` definition locks a record `FOR UPDATE`, then takes namespace-4 `key` advisory lock (`db/phase2/008_change_hardening_b.sql:290-335`). Migration 027 now defines an ungranted fenced `validate_v1` plus a replacement for the still-granted legacy signature that delegates to the same versioned implementation. Both candidate routes take namespace 2/7/lifecycle and global change-ID/key locks before relation rows, then revalidate the record/business-key snapshots. This is source only: migration application, mixed-process rollout, installed grants, and runtime ordering remain unverified; the historical migration is not rewritten.
2. The event-chain trigger `events_chain` is created at `db/phase2/004_change_ledger.sql:190-191`; its final body takes the chain advisory lock (`db/phase2/008_change_hardening_b.sql:1524-1532`, later definition in `011`). The lifecycle trigger is created/redefined at `db/phase2/022_lifecycle_epoch_fence.sql:149-152` and `db/phase2/024_restore_caller_lock_timeout.sql:52-61`. PostgreSQL fires same-event triggers alphabetically, so current source requests the chain advisory lock before `events_lifecycle_fence_guard` requests the lifecycle-row shared lock. A path lacking an earlier lifecycle lock can wait while holding the chain lock; no live deadlock was reproduced. Candidate resolution is a coordinated cutover: keep current guards through additive qualification; after every runtime mutator has a versioned entry and legacy function/direct-table rights are revoked, drop both row-locking lifecycle triggers and move lifecycle/permit-epoch validation into trusted entries immediately after namespaces 2/8/7 and before row/DML work. The existing event-chain guard then remains the final contended lock. Implementation and qualification remain open. [PostgreSQL trigger behavior](https://www.postgresql.org/docs/16/trigger-definition.html).
3. `verifier_key_receipt_role_guard` takes an advisory transaction lock on key material from a row trigger (`db/phase2/017_receipt_hardening.sql:38-54`). That lock must be included in the key mutation order. Do not infer an opposite-path deadlock from this lock alone.
4. Lifecycle triggers cover event inserts and permit insert/update paths, not every granted mutation API. Many record, registry, evidence, budget, hold, key, observation, and recovery APIs lack proof of acquiring one common scope fence before row locks; the source coverage map already identifies this gap (`docs/phase2/S13_API_MUTATION_FENCE_COVERAGE_2026-10-17.md:18-43`).
5. The legacy fixed row order is not compatible with the full FK graph: `records.base_fingerprint` references `targets` (`004:247`), `records` has self-FKs (`004:222-223`, `008:1865-1870`), and `claim_tokens.change_id` references `records` (`004:309-315`). An additive lock contract must derive FK SCCs from its exact schema and use parent-component-before-child-component ordering; it cannot retain claim-token-before-record as a universal row rank.

### UPSERT and unique-conflict paths

The final granted mutation paths contain these conflict-arbitration points. `DO UPDATE` applies its update action when any attached `WHERE` predicate passes; otherwise the conflicting row is not updated. `DO NOTHING` skips insertion for the conflict. PostgreSQL documents that conflicting unique-index activity can block and that `ON CONFLICT DO UPDATE` provides an atomic insert-or-update outcome ([PostgreSQL 16 INSERT](https://www.postgresql.org/docs/16/sql-insert.html)). These per-key arbitration points do not define a stable cross-table lock order.
