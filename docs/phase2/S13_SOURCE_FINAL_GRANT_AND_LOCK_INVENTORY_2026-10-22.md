## Scope and conclusion

It is not a live catalog query. It does not establish which migrations are installed, role membership, owner/admin access, effective deployed grants, or runtime lock behavior.

## Lock-order findings

Migration 008 states the intended order as named namespace advisory locks, claim-token rows, records, secondary rows, and the event-chain advisory lock last (`db/phase2/008_change_hardening_b.sql:3-15`). Static source review found these contradictions:

1. The final `validate(text,text,uuid)` definition locks a record `FOR UPDATE`, then takes the named `key` advisory lock (`db/phase2/008_change_hardening_b.sql:290-335`). This violates the documented named-advisory-before-row order. The reviewed source does not by itself prove a reachable deadlock cycle; the uniform order is nevertheless unproven.
2. The event-chain trigger `events_chain` is created at `db/phase2/004_change_ledger.sql:190-191`; its final body takes the chain advisory lock (`db/phase2/008_change_hardening_b.sql:1524-1532`, later definition in `011`). The lifecycle trigger is created/redefined at `db/phase2/022_lifecycle_epoch_fence.sql:149-152` and `db/phase2/024_restore_caller_lock_timeout.sql:52-61`. PostgreSQL fires same-event triggers alphabetically by trigger name, so within the event-trigger sequence `events_chain` requests the chain advisory lock before `events_lifecycle_fence_guard` requests the lifecycle-row shared lock. A path that has not already acquired the lifecycle-row lock can wait for it while holding the chain lock. Some paths, such as a permit mutation, may acquire the lifecycle-row lock earlier in the same transaction; this statement describes relative trigger requests, not the lock state of every event writer. The trigger sequence conflicts with the chain-last rule. Recovery activation is disabled; no live deadlock was reproduced or established. [PostgreSQL trigger behavior](https://www.postgresql.org/docs/16/trigger-definition.html).
3. `verifier_key_receipt_role_guard` takes an advisory transaction lock on key material from a row trigger (`db/phase2/017_receipt_hardening.sql:38-54`). That lock must be included in the key mutation order. Do not infer an opposite-path deadlock from this lock alone.
4. Lifecycle triggers cover event inserts and permit insert/update paths, not every granted mutation API. Many record, registry, evidence, budget, hold, key, observation, and recovery APIs lack proof of acquiring one common scope fence before row locks; the source coverage map already identifies this gap (`docs/phase2/S13_API_MUTATION_FENCE_COVERAGE_2026-10-17.md:18-43`).

### Recovery and stale-revoke helper crosswalk

The recovery worker `recover_sweep(text,text,jsonb)` takes `A:sweep`, selects bounded batches, locks expired approval nonces, then batch claim tokens and records before processing per-item stages (`020:54-142`). Its stage-to-leaf effects are:

- **T5x:** `release_claim_internal` (`020:145-160`; final helper `006:128-151`) locks token then record, calls `release_zero_effect` (`004:446-470`) to release reservation/target/key/lease effects, updates record and appends the release event.
- **T6c / T6r:** `cancel_permit` (`020:162-177`; `008:909-932`) and `permit_not_issued_internal` (`020:179-191`; `008:934-958`) lock tokens and record, update permit/token/record state, release zero-effect resources and append events. The permit lifecycle/fence/verified guards run on CAS updates; these transitions do not enter the `PERMITTED → DISPATCHED` call-deadline branch.
- **T9:** locks record, marks the expired call `APPLY_UNKNOWN`, inserts `CALL_OWNERSHIP` hold when needed and appends `HARD_DEADLINE_UNKNOWN` (`020:193-226`).
- **T3 / VOID:** lock record, update expired/void state and append the corresponding event (`020:228-263`).
- **T12:** locks record and the RESOLVE counter, increments attempts or calls `triage_internal` at the limit; the helper updates record/counter and appends a triage event (`020:264-312`; `006:181-194`).
- **GAP_BOUND:** scans aged open holds, inserts/uses a bounded counter and appends `ANCHOR_GAP_BOUND_EXCEEDED` once per hold (`020:314-343`).
- **GAP:** calls `triage_internal`, which updates record/counter and appends an event (`020:344-358`; `006:181-194`).
- **VERIFY:** locks record and VERIFY counter, then calls `verify_attempt_internal`; that helper updates counter and may close the record, insert a halt hold and append an event (`020:359-389`; `012:248-285`).
- Per-item exception handling calls `sweep_item_failed`, which upserts `sweep_failures` and appends `SWEEP_ITEM_FAILED` (`008:893-906`). The final `sweep_runs` insert is not itself followed by an event (`020:437-448`).

`revoke_stale` takes `A:sweep`, selects at most 200 candidates, batch-locks tokens then records, and invokes `revoke_core` (`020:9-36`). That helper locks tokens by generation then the record, releases zero-effect reservation/target/lease resources where applicable, updates the record and appends `REVOKED` (`008:1014-1040`; `004:446-474`). Per-item failures upsert the failure row and append a failure event (`008:893-906`).

This is the stage-to-leaf crosswalk found in the reviewed final source. It describes written SQL order; actual concurrent wait graphs and database schedules remain runtime questions.

### UPSERT and unique-conflict paths

The final granted mutation paths contain these conflict-arbitration points. `DO UPDATE` applies its update action when any attached `WHERE` predicate passes; otherwise the conflicting row is not updated. `DO NOTHING` skips insertion for the conflict. PostgreSQL documents that conflicting unique-index activity can block and that `ON CONFLICT DO UPDATE` provides an atomic insert-or-update outcome ([PostgreSQL 16 INSERT](https://www.postgresql.org/docs/16/sql-insert.html)). These per-key arbitration points do not define a stable cross-table lock order.

- **Budget/claim:** `claim` upserts `reservations` by `change_id`, conditional on a released prior row (`009:542-552`); `declare_budget` upserts `change_budget` by `change_id` (`008:174-179`). `budget_admin` uses a grant row lock followed by update-or-insert and event append; it is not an UPSERT (`008:623-644`).
- **Business keys and overrides:** `declare_business_key` upserts by `change_id` after record lock (`005:500-535`); `bind_duplicate_override` uses untargeted `DO NOTHING` but still appends `OVERRIDE_BOUND` after a skipped insert (`005:546-561`).
- **Registry and epochs:** principal/target core uses `DO UPDATE` on the tenant/company/principal or base-fingerprint key, then upserts the epoch row (`010:148-185`; `008:1068-1077`). `enforce_registry` upserts `registry_policy` by tenant/company and appends an event (`008:75-88`).
- **Permit/deadline:** `begin_apply` inserts a permit with `DO NOTHING` on `(change_id,generation)` and appends APPLYING even on conflict (`009:677-681`); the dispatch fence trigger inserts a call deadline with `DO NOTHING` when a permit transitions `PERMITTED → DISPATCHED` (`008:1746-1768`).
- **Recovery state:** RESOLVE/ANCHOR_GAP/VERIFY counters use `DO NOTHING` on `(subject_id,kind)` and mutable stages then read or explicitly lock the counter (`020:277-280,322-324,370-374`); `complete_lock_busy` also inserts/locks its LOCK_BUSY counter before update and event (`008:987-1000`). Sweep-failure upsert increments failures on `(subject_id,stage)` before its event (`008:893-906`).
- **Operator policy/state:** `set_sweep_policy` selects an existing row `FOR UPDATE`, upserts `(tenant_id,company_id)` and appends an event (`012:236-244`); `kill_switch` upserts the same scope key after OFF-path sweep processing and appends an event (`020:478-484`).
- **Evidence and receipts:** `record_evidence` does `DO NOTHING` on `(change_id,kind,content_hash)` and returns an existing row without an event; new rows append one (`019:74-88`). `verify_dispatch_payload` does `DO NOTHING` on `(change_id,generation,payload_digest)` and appends only for a returned new row (`012:125-134`). Receipt requirements and claim-generation carry use `DO NOTHING` on `(change_id,generation)` (`016:106-115`; `017:19-35`).
- **Target observations:** `observe_target` inserts by `(change_id,generation) DO NOTHING` and appends `TARGET_OBSERVED` after the statement even when conflict skips the insert (`005:377-402`).
- **Verification counters:** `verify_attempt_internal` inserts a VERIFY counter with `DO NOTHING`, then explicitly locks it `FOR UPDATE` before changing attempts/deadlines (`012:248-285`).

The source identifies conflict keys and whether later explicit row locks/events occur. It cannot prove deployed unique-index definitions, schema drift, actual wait-for graphs, or a globally deterministic order across concurrent conflicts.
