## Batch A (migration 007_change_hardening_a.sql): evidence, digests, checkpoint gate, state guards

A1 (M, SEC-F1, SEC-F2, REL-F4, REL-F5, DB-M1, DB-M2): signed-evidence layer is bypassable. Raw `complete`, `resolve_unknown`, `verify`, `witness_cosign`, `retry_verify`, `verify_inconclusive`, `complete_lock_busy` stay granted and accept caller JSON; `complete_signed` does not read the record content; the signature covers `content_hash` but `content_hash` is never checked against `content`; the binding lacks generation and call_id; the outcome and verdict come from caller flags (`p_outcome`, `p_passed`, `p_present`). Required: revoke EXECUTE of raw variants from runtime roles (keep them internal, callable only by the signed wrappers); `record_evidence` verifies `content_hash = sha256(content)`; the binding includes generation and call_id; the ledger parses typed content: SUCCESS needs a result-returned record for this call_id and generation; PRE_WRITE_REFUSAL needs stage = PRE_WRITE, a closed-set refusal code and a non-empty no-effect proof; T11 and T16 absent need a signed OBSERVATION record with effect_present = false plus a class a or b completion proof; verdicts derive from the records, not from flags; `complete_lock_busy` and `retry_verify` take evidence ids. Port SPEC updated. Acceptance: each raw function as its former role raises 42501 (port maps to NOT_ENTITLED); a SUCCESS record used for PRE_WRITE_REFUSAL is refused; another generation or call_id is refused; a record whose content_hash does not hash its content is refused; `operator_resolve(present=false)` without a signed observation raises COMPLETION_PROOF_MISSING.

A2 (M, REL-F1): a finished change can be re-approved and re-claimed (second dispatch). `approve` and `issue_approval_nonce` must require authorization in (NONE, VOIDED, REVOKED) and execution NOT_STARTED. (`claim` guards are in batch B.) Acceptance: for FAILED_APPLY, VERIFIED, APPLYING, TRIAGE_REQUIRED, approve and nonce issuance raise FORBIDDEN_TRANSITION.

A3 (M, REL-F2): `verify` and `verify_signed` can flip FAILED_VERIFY to VERIFIED, leaving an unreleasable halt, duplicate halts or a leaked repair lock. Require verification_state = NOT_VERIFIED (otherwise return the stored state or FORBIDDEN_TRANSITION); halt insert idempotent. Acceptance: verify(true) on FAILED_VERIFY refused; two verify(false) calls leave exactly one open halt.

A4 (M, REL-F3): T11 and T16-absent on a repair delete the target lock instead of handing it back to the parent (the offline model hands back). Use the handback for repair changes in `resolve_unknown`, `operator_resolve`. Acceptance: after T11 or T16-absent on a repair, the target lock owner is the parent, the halt is open, and a new repair claim succeeds.

A5 (M, DB-M7): NULL comparisons fail open (`p_generation <> rec.claim_generation` with NULL skips the fence; `IF NOT p_present` with NULL takes the present branch). Use IS DISTINCT FROM and raise SCHEMA_INVALID on NULL inputs. Acceptance: `complete(..., NULL generation)` and `operator_resolve(..., NULL present)` refused and change nothing.

A6 (M, SEC-F3, DB-M9): the checkpoint and permit gate is forgeable: `record_checkpoint` stores caller-supplied sink_kind, read_back and signature; worker can read `ledger_head`, record its own REAL checkpoint and call `issue_permit`; `attach_permit_signature` has no key check. Required: a dedicated checkpoint identity (new role) is the only one that can call `record_checkpoint` and `attach_permit_signature`; the ledger verifies the checkpoint signature (keyed-hash stand-in registered in verifier keys until D9 supplies Ed25519) against a registered key before setting sink_kind = REAL and read_back_confirmed; `issue_permit` is internal or refuses a checkpoint row not written by the checkpoint identity; worker/writer lose `record_checkpoint`. Port SPEC and DispatchGate updated. Acceptance: worker or writer calling `record_checkpoint(..., 'REAL', true)` raises NOT_ENTITLED; `issue_permit` with a row not written by the checkpoint identity raises CHECKPOINT_UNAVAILABLE; bad signature refused.

A7 (M, SEC-F4): SQL approval binds only the opaque requester-supplied payload_digest. Compute the approval digest in SQL (or recompute and compare at propose) over change_id, kind, scope, target_ref, target_version, parent_change_id, repair_for, expires_at, payload digest, business_state_digest, rule-table version and the server-derived allowed effects; `approve` compares against it; `read_status` returns those fields. Acceptance: two POSTs with the same target_version and different target_ref give different digests; approve with another change's digest raises DIGEST_MISMATCH. Reconcile with the offline `approval_digest` in src/business_ai_gateway/phase2/change/proposal.py (use the same canonical field set; document any deliberate difference).

A8 (m, DB-M2 part, SEC-F6 part): `consume_two_person_cosign` (006) compares role names only and never checks capabilities; use `same_person`, the operator and recovery_witness capabilities and the active/registered checks from 005. Acceptance: with the registry enforced, two aliases of one person raise APPROVER_NOT_INDEPENDENT; a witness lacking the capability raises NOT_ENTITLED.

## Batch B (migration 008_change_hardening_b.sql): claim and budget, registry default, anchor release, sweep robustness, minors

B1 (M, REL-F7, DB-M3, SEC-F5): `claim` and `validate` take budget inputs from the requester and skip the gate on NULL. Derive grant, amount, counts, currency and business-key hash from the stored change; refuse claim without a RESERVED row (BUDGET_EXCEEDED); check the grant currency (CURRENCY_NOT_BUDGETED); `validate` computes the budget pre-check itself (remove `p_budget_ok`, `p_duplicate` from the external signature); a CREATE_DRAFT without a business key cannot reach VALIDATED or claim (key lock mandatory); `records.reservation_state` changes only when a reservation row exists (equality of records.reservation_state and reservations.state after every path). `claim` also requires execution NOT_STARTED, verification NOT_VERIFIED and dispatch not DISPATCHED (REL-F1). Acceptance: claim with NULL grant or a changed amount refused; draft without business key cannot validate; claim on a FAILED_APPLY/VERIFIED change raises FORBIDDEN_TRANSITION.

B2 (M, DB-M4, SEC-F7): `budget_admin` has no scope check and can overwrite another tenant's grant, and appends no ledger event; helpers `person_of`, `same_person`, `epoch_value`, `registry_enforced` skip assert_scope. Add assert_scope, restrict the conflict update to the same tenant and company, add a REVOKED path, append an event, scope the helpers or revoke external grants. Acceptance: operator scoped to A updating a B grant raises SCOPE_NOT_GRANTED; every limit change is an event in verify_chain.

B3 (M, DB-M8, SEC-F6): the registry defaults to fail-open and independence falls back to role-name equality; `caller_role()` honors SET ROLE. Default new scopes to enforced; claim and issue_permit refuse when the registry is not enforced for any target class other than the disposable clone; registry changes require two-person control or a fixed list; identity derives from session_user (or a registered principal). Acceptance: a scope with no registry_policy row refuses unregistered actors; a self-approval via SET ROLE raises NOT_ENTITLED or APPROVER_NOT_INDEPENDENT. Existing tests that rely on legacy mode must be updated deliberately (register principals in their fixtures).

B4 (M, REL-F6): ANCHOR_GAP from `check_anchor` (W10) can be released by a fresh checkpoint of the restored head without reconciling the lost head. Persist the external (seq, hash) with the hold; release only when the ledger contains that exact event, or via the two-person operator path with evidence. Acceptance: restore an older ledger snapshot, run check_anchor, record a new checkpoint, release_hold is refused.

B5 (M, REL-F8, DB-M5, DB-M6, SEC-F10): lock-order inversion between the chain advisory lock and row locks (sweep appends an event, then locks the next record; api functions lock rows then append; token-vs-record order inverted in begin_apply, release_claim_internal vs cancel_permit and permit_not_issued_internal; bump_epoch vs register_principal), unbounded sweep loops in one transaction, no per-item isolation (one poisoned repair row starves T9/T12 and rolls back counters), caller-tunable timing bounds. Define one lock order (row locks first, chain lock last, token before record everywhere) and document it in a header comment; sweep processes bounded batches, one subtransaction per item (BEGIN ... EXCEPTION), records a committed failure event/counter for a failing item and continues; contract constants (claim TTL 120 s, permit TTL 60 s, T12 5 attempts/15 min, anchor window 15 min, verify bound 3) are ledger constants or an operator-set policy row, not worker parameters; JSON overrides validated (SCHEMA_INVALID, not 22P02). Acceptance: a two-session test with a sweep concurrent with complete calls and a begin_apply replay shows no 40P01 over N rounds; a poisoned row plus an expired T9 item still moves the T9 item; worker passing verify_max_attempts=1 is refused.

B6 (m, REL-F9, DB-minors): (a) ROLLBACK_REFUSED reachable at T8 for UNPOST precondition refusals (SQL currently ends FAILED_APPLY); (b) `reject` allowed from APPROVED (contract and offline model); (c) kill-switch STOP_ADMIT/STOP_EFFECTS unwinds CLAIMED and PERMITTED states immediately in the sweep (T5x/T6c/T6r), not after TTL; (d) nonce EXPIRED persisted without a raise that rolls it back; (e) replays idempotent: repeated approve, claim, issue_permit return the existing result; concurrent propose with one logical key returns the replay instead of a raw unique violation; begin_apply replay on a dead change refused; (f) permit and dispatch re-run the repair authorization (hold and repair checks), as the offline model does at PERMIT and WRITER phases; (g) T6 ownership row stores the pre-image hashes and host/session columns; (h) verification attempts counted from real attempts, not sweep ticks; (i) partial unique index on open holds per (tenant, company, base, cause, change); (j) tenant integrity: UNIQUE(tenant_id, company_id, change_id) on records and composite references in child tables and a tenant filter in the parent-VERIFIED guard and parent_change_id validation at propose; (k) requesters and approvers lose direct SELECT on records, claim_tokens, holds (or an own-change policy) so reads go through read_status; (l) TEST_LANE_AUTO approval type derived server-side, allowed only for a clone target, persisted in the approval and event (MFA flag likewise); (m) the hash also covers tenant_id, company_id, event_id and recorded_at, or document why not; bound evidence payload size before the terminal transition; (n) advisory lock keys use the two-int form with a namespace constant; (o) TRUNCATE guards on checkpoints, approvals, change_closures, override_bindings; (p) indexes: claim_tokens(state) partial ISSUED, dispatch_permits(expires_at) partial PERMITTED, records partial indexes on execution_state and expires_at, reservations(grant_id), approvals(change_id), witness_cosigns(change_id), records(repair_for), records(parent_change_id), sweep_runs; (q) port: refuse or RESET ROLE when the connection is already in a transaction. Each item needs a focused test or an explicit "not applicable, reason" in the report.
