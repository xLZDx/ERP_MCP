# S13 PostgreSQL admission and barrier schema design

Date: 2026-10-22. Last amended: 2026-10-24. Status: implementation design proposal; not migration approval or S13 acceptance.

## Goal and non-goals

Define durable PostgreSQL state for the private Ivan writer service without adding a second authorization claim or holding a database transaction across COM. Keep S12's `PERMITTED → DISPATCHED` compare-and-set (CAS) as the single authorization point. This design does not enable recovery, `READY`, listener deployment, physical COM calls, or any production write path.

## Current behavior and constraints

- `db/phase2/004_change_ledger.sql` stores one `dispatch_permits` row per `(change_id, generation)`, including its `call_id`; `record_call` in migrations 004/012 checks the permit and performs the `PERMITTED → DISPATCHED` CAS, updates the record, and appends `DISPATCHED` in the same transaction.
- That source path does not persist a `dispatch_cas_id`, authenticated writer-process binding, or durable COM invocation stage. S12 freeze §3.2 and §5 require an immutable dispatch-attempt/CAS identity bound to the writer process and call; each `call_id` is globally non-reusable across generations and scopes.
- `src/erp_mcp_private_writer/service.py` defines the coordinator and `AdmissionStore` contract; `src/erp_mcp_private_writer/postgres_store.py` is a source-only adapter implementation. No S13 schema/routines or runtime grants are installed, so the adapter is not operational. Its records must not become an independent authorization source.
- The S13 common lock proposal is in `S13_SCOPE_FENCE_IMPLEMENTATION_DESIGN_2026-10-22.md`. A new schema is not safe until all mutation, trigger, unique-conflict, and recovery paths acquire that fence in the accepted order.

## Options and decision

1. **Separate admission table as a second claim.** Rejected: its insert could disagree with the ledger CAS, creating two competing authorization sources and a crash window.
2. **Use only the existing permit row.** Rejected as incomplete: source currently has no immutable CAS identity, authenticated process binding, invocation-stage guard, or barrier history needed to distinguish accepted, invoked, and uncertain calls after restart.
3. **Extend the S12 CAS into the durable dispatch-attempt record — selected for implementation design.** In one fenced top-level transaction, the S12 CAS creates exactly one immutable `dispatch_cas_id` attempt bound to the existing permit/call tuple and authenticated service process. This row is the durable representation of the existing authorization transition, not a second claim. Monotonic invocation/result fields or append-only attempt events track physical progress but cannot make an unpermitted call authorized.

### Exclusive service-instance startup epoch

The scope lifecycle epoch fences stale business requests; it does not elect one live writer process. Add a separate process-serving fence keyed by the configured writer-service identity and authenticated base fingerprint. A startup transaction begins at `READ COMMITTED`, then takes an exclusive row lock on that serving-fence row, atomically increments `service_epoch`, binds the new non-reusable `service_instance_id`, and returns the complete unresolved-attempt and open-barrier inventory plus a database-issued readiness reference. It does not overwrite or terminalize attempt evidence. Each dispatch attempt stores the serving epoch and process instance that won its durable CAS.

Every admission and `mark_invoking` transition first follows the accepted namespace advisory order (including the exclusive per-scope fence), then takes a shared row lock on the active serving-fence row before claim/record row locks and compares the authenticated service instance and supplied epoch with its current values. Startup takes only the exclusive serving-fence row lock and does not acquire advisory/scope locks, so it can wait for these short top-level transactions without a reverse lock-order edge. The `READ COMMITTED` inventory query runs after the exclusive epoch update has serialized with old admission/invocation transactions. A newer startup fences an older process from new admission and from entering COM after restart takeover. It cannot revoke a COM call whose `mark_invoking` CAS already committed; such a call remains `POSSIBLY_EXECUTING` in the startup inventory until exact S12 evidence resolves it. Startup serves only when the complete inventory has no unresolved calls or open barriers and the database validates readiness. This process-serving epoch is distinct from the tenant/company lifecycle epoch and cannot authorize a call or advance lifecycle readiness by itself.

## Design

### Dispatch attempt

- Add `private_writer_dispatch_intents` as the immutable, non-authorizing intent/checkpoint row created in the retained S12 begin-apply transaction before checkpoint and permit issuance. Fields: `tenant_id`, `company_id`, `organization_ref`, `base_fingerprint` text NOT NULL; `change_id`, `call_id` uuid NOT NULL; `claim_generation`, `dispatch_generation`, `auth_epoch` bigint NOT NULL CHECK (>0); closed `operation_kind`; lowercase 64-hex `approval_digest`, `payload_digest`; nullable `target_ref`, `expected_pre_version`; and `created_at`. Primary key is `dispatch_intent_id uuid`; unique keys include `(change_id,claim_generation)`, `(change_id,dispatch_generation)`, global `call_id`, and `(dispatch_intent_id,change_id,claim_generation,dispatch_generation,call_id,payload_digest)`. Allocate `dispatch_generation` as a positive, non-reused per-`change_id` intent ordinal while the existing record row is locked; a committed intent consumes that ordinal even if no permit or physical call later occurs, so gaps are valid. It is distinct from claim generation and is never inferred from it. Narrow FKs use existing keys `change_id → records(change_id)` and `(change_id,claim_generation) → dispatch_permits(change_id,generation)`; insertion locks the record and permit-independent authorization rows and verifies scope, operation, target/version, payload, approval and epoch against authoritative stored values. The checkpoint covers this immutable pre-permit tuple. After its successful read-back, the versioned permit-issuance transaction creates `permit_id uuid` before ranked locks, locks the existing S12 permit, issues the digest, and inserts one immutable `private_writer_permit_bindings` child with `dispatch_intent_id uuid PRIMARY KEY REFERENCES private_writer_dispatch_intents`, `permit_id uuid UNIQUE`, `permit_digest`, `checkpoint_seq`, signer key/version, issued/expiry times; it cross-checks S12 permit state/digest and the same intent before commit. This child is the authoritative source of permit ID/digest (legacy `dispatch_permits` has no `permit_id` column). The versioned routine returns the stored ID on exact retry and supports lookup by `dispatch_intent_id` after a lost response; changed digest/tuple conflicts before any second permit. The primary key rejects a second binding for one intent even if its permit ID/digest differs. No permit-binding row exists before issue time, and neither parent nor child is updated or replaced on retry. The intent and permit binding grant no authorization and do not change the S12 `PERMITTED → DISPATCHED` CAS.
- The attempt copies immutable identity fields from the intent and permit ID/digest from its exact `private_writer_permit_bindings` child. Its FK targets are exact and available: intent unique key `(dispatch_intent_id,change_id,claim_generation,dispatch_generation,call_id,payload_digest)`; permit-binding unique key `(dispatch_intent_id,permit_id,permit_digest)`; and attempt unique key `(dispatch_cas_id,dispatch_intent_id,change_id,claim_generation,dispatch_generation,call_id,payload_digest,permit_id,permit_digest)`. Admission validates both exact FKs, locks record/permit/intent/binding in the accepted order, rechecks the copied scope/operation/target/version/approval/payload/epoch and permit digest, then performs the CAS and attempt insert atomically.
- Add an additive `dispatch_attempts` relation owned by the ledger owner, with RLS forced and no direct runtime table grants. Bind the immutable identity to `private_writer_dispatch_intents` and its narrow existing record/permit parents. Declare `call_id UUID NOT NULL` and enforce global `UNIQUE(call_id)` (ordinary PostgreSQL `UNIQUE` permits multiple nulls); also enforce unique `dispatch_cas_id` and `(base_fingerprint, dispatch_cas_id)`, plus one attempt per permitted call/generation.
- The v1 attempt row contract is: `dispatch_cas_id uuid PRIMARY KEY`; `dispatch_intent_id`, `permit_id` uuid NOT NULL; full immutable identity fields copied from the intent, including `payload_digest`; permit ID/digest copied from the exact permit-binding child; authenticated `session_user`, service/host/process-instance IDs; `service_epoch bigint CHECK (>0)`; nullable `onec_session_instance_id`; `state` closed to `ACCEPTED_NOT_INVOKED|POSSIBLY_EXECUTING|TERMINAL_WITH_EVIDENCE`; `invocation_started_at timestamptz NULL`; `terminalized_at timestamptz NULL`; and `created_at timestamptz NOT NULL`. Its exact candidate unique/FK targets are enumerated above; `(base_fingerprint,call_id,dispatch_cas_id)` is unique for barrier membership. Narrow authoritative parent FKs are `change_id → records(change_id)` and `(change_id,claim_generation) → dispatch_permits(change_id,generation)`; no composite FK targets a key absent from legacy tables. The admission function locks record, permit, intent and issued-permit binding, then validates every copied value before the CAS/insert. `claim_generation` and `dispatch_generation` are independent S12 values and are checked against the exact intent and signed evidence; do not equate them. A row check requires `invocation_started_at IS NULL` exactly in `ACCEPTED_NOT_INVOKED`, non-NULL in `POSSIBLY_EXECUTING`; `terminalized_at IS NULL` until terminal state and non-NULL in `TERMINAL_WITH_EVIDENCE`. A direct `ACCEPTED_NOT_INVOKED → TERMINAL_WITH_EVIDENCE` is allowed only for validated no-entry evidence; it has no invocation timestamp but does have `terminalized_at`. Receipt/terminal evidence references live only in `private_writer_attempt_evidence`; the API's `evidence_ref` is a deterministic projection of that immutable child set. The state transition function/trigger requires an attached `WRITER_RECEIPT` association before recording a receipt result and the complete validated purpose-specific evidence set before terminal state. Immutable identity/owner/permit columns never change; no lease expiry resets state. Evidence refs have composite FKs to the S13 evidence registry defined below. These are candidate DDL requirements, not deployed-schema claims.
- Do not persist a second `admission_id`: no other source consumer or S12 identity uses it and the immutable `dispatch_cas_id` already identifies the winning admission. The source and adapter contract omit it; inventing a second global ID and conflict domain would add no acceptance property.
- `dispatch_cas_id` is allocated as a canonical UUID before ranked locks and is globally unique across all bases/scopes. Admission takes namespace-6 key `dispatch-cas-id:v1:<lowercase-canonical-uuid>` with the planned call/change IDs before relation rows; it passes this exact ID to the immutable attempt INSERT. The global unique constraint is authoritative; namespace-6 is ordering only. Exact immutable replay is lookup-only, while any cross-scope reuse or changed attempt tuple fails closed.
- Enforce global `call_id` non-reuse at immutable intent creation, earlier than dispatch: the committed `private_writer_dispatch_intents` row reserves that canonical UUID permanently across generations and scopes, including when checkpoint/permit issuance is later abandoned. Namespace-6 `call-id:v1:<uuid>` locking plus the global unique constraint on intents rejects any later reuse; the attempt FK binds to that same reservation. Exact begin-apply replay returns the original intent lookup-only; an intent with a missing permit is not silently deleted or recycled and cannot authorize COM. Permit issuance replay returns its original immutable binding/permit ID; a changed digest or tuple conflicts. No terminal transition releases the ID.
- Add a `physical_base_slots` relation with `base_fingerprint` as primary key, nullable unique `active_dispatch_cas_id`, nullable `open_barrier_id`, and `admission_closed boolean NOT NULL`. Add `UNIQUE(base_fingerprint, active_dispatch_cas_id)` and composite FK `(base_fingerprint, active_dispatch_cas_id) → dispatch_attempts(base_fingerprint, dispatch_cas_id)`; nullable active IDs skip the FK when no call is active. Add composite FK `(base_fingerprint, open_barrier_id) → writer_barriers(base_fingerprint, barrier_id)`, also nullable only when no barrier is open. Require `admission_closed = (open_barrier_id IS NOT NULL)`; there is no valid committed intermediate state where only one is set. Admission leaves both clear; barrier closure sets both atomically after inserting the parent; successful finalization clears both atomically. Ordinary mutation cannot clear either field. A transition guard forbids clearing the active CAS except through a terminal-evidence routine. One row per fingerprint plus the composite active-CAS pointer enforces at most one unresolved physical call across every tenant/company scope mapped to that base. `admit` takes namespace 8 before namespace 7, revalidates the database-authenticated base binding, and atomically claims this slot with the S12 CAS and attempt insert. An identical replay by the owning call returns its existing status; a different call receives `BASE_CALL_IN_PROGRESS` while the slot is occupied. Namespace-8 hash collisions add serialization only; the authenticated base fingerprint and row key define authority.
- Preserve namespace 5 for the existing recovery-sweep lock; namespace 8 orders the authenticated physical-base slot/barrier before the new exclusive per-scope mutation/recovery fence in namespace 7. Replace the implementation of the writer's S12 `record_call` entry point through a versioned additive function (do not edit historical migrations). A physical-writer admission takes the exact shared namespace-2 switch key first, then namespace 8, then the exclusive scope-7 fence, and immediately locks/validates the lifecycle row before verifier-material or other relation locks; it then takes each planned existing verifier-material bigint lock (exact `hashtextextended(key_material, 17017)` identity, deduplicated and signed-bigint sorted; registration paths pre-acquire before verifier row/index work), followed by namespace-6 locks for canonical `call_id` and `change_id`, locks the serving row and remaining FK-SCC rows in their accepted order, validates the exact permit and epoch, performs the existing CAS, and inserts the attempt plus audit event in the same transaction. Sweep/recovery paths retain their compatible namespace-2 → namespace-7 → lifecycle-row → namespace-5 → namespace-6 order; private physical-base recovery adds namespace 8 before namespace 7, and the kill-switch-held recovery helper must not reacquire namespace 2. A replay with identical identity returns the same attempt; any conflicting reuse fails closed. The old entry point is revoked only in the additive migration after dependent callers are migrated and grants are reconciled.
- Bind the authenticated `session_user`, registered writer service/host identity, and a non-reusable writer process-instance UUID to the attempt. Never accept those values as trusted caller assertions. A database role/service authentication binding must establish them before dispatch; the physical call remains forbidden when identity validation is unavailable.
- Define `private_writer_service_bindings` before the serving fence: `session_user name PRIMARY KEY`, `base_fingerprint text UNIQUE NOT NULL`, `writer_service_id text NOT NULL`, `writer_host_id text NOT NULL`, `binding_enabled boolean NOT NULL CHECK(binding_enabled=true)` while present, `created_at`, and nullable revocation timestamp; add `UNIQUE(session_user,base_fingerprint,writer_service_id,writer_host_id,binding_enabled)`. Only the separate identity-administration owner may mutate it. Use one LOGIN principal and one client certificate per exact service/host/base tuple; do not share one login across multiple bases. PostgreSQL client-certificate/`pg_hba.conf` identity must map the certificate to that exact login, with no membership or `SET ROLE` path to another binding. S13 routines derive service, host and base from `session_user` and reject conflicting identity arguments; a caller-supplied instance UUID remains only a comparison value. Do not infer host identity from a caller text parameter or from a shared login. The runtime binding row and effective login/member grants must be measured in the disposable qualification.
- Define `private_writer_serving_fences` with primary key `(writer_service_id, base_fingerprint)`, authenticated `session_user name`, authenticated `writer_host_id text`, `service_instance_id text`, positive `service_epoch bigint`, `started_at timestamptz`, `readiness_ref uuid NULL CHECK(readiness_ref IS NULL OR readiness_ref<>zero UUID)`, and `binding_enabled boolean NOT NULL CHECK(binding_enabled=true)`; its composite FK `(session_user,base_fingerprint,writer_service_id,writer_host_id,binding_enabled)` references the exact unique binding tuple. Process-instance UUID text must be canonical lowercase with supported UUID version and RFC variant bits. A single-row `FOR UPDATE` startup transaction increments the epoch and replaces the instance/readiness reference. The service/host/base/session tuple is immutable for one fence key; only the startup security-definer routine changes instance/epoch. Every admission, invocation and terminal transition locks this exact row in the mode defined above. Caller input is never authoritative for mapping.
- `mark_invoking` is a conditional monotonic transition on the exact `(dispatch_cas_id, process_instance_id)` from `ACCEPTED_NOT_INVOKED` to `POSSIBLY_EXECUTING`. Only the winning service process may cross the COM invocation boundary. A retry or a different process only reads the prior state. Once invocation may have started, no lease expiry or process death returns the attempt to a dispatchable state.
- The additive signed-witness path preserves T16 while making retries deterministic. Its request identity is `(change_id, authenticated signer, signer_session, completion_evidence_id)`, where the signer is the trusted `caller_role()` result, `signer_session` is populated from `session_user` by the trusted insert path, and `completion_evidence_id` is the exact immutable current-generation `COMPLETION_PROOF` ID. The candidate partial unique index is on `(change_id, signer, signer_session, (completion_proof->>'evidence_id'))` for rows with non-null `signer_session` and an `evidence_id` proof field; the signed entry requires that field to be a canonical UUID. It returns the same immutable `cosign_id` for an exact retry, including after a lost response; lookup is read-only and does not recreate or unconsume a cosign. A different evidence ID is a distinct submission and must independently pass the current generation/permit checks. If the same request identity resolves to a different stored proof envelope, refuse as `COSIGN_REPLAY_MISMATCH`. Before creating the index, the additive migration must detect duplicate legacy tuples and fail without deleting or rewriting history if any are ambiguous. `operator_resolve` continues to consume one exact unconsumed `cosign_id` and applies the existing T16 person-independence rules.
- `record_terminal` accepts only S12-validated signed receipt/evidence references bound to that exact attempt. A write result alone is not terminal proof. Reconciliation appends evidence and never replaces an accepted receipt or proof.
- **Signed evidence registry and validation boundary.** S12 `TrustedIdentityRegistry` is explicitly an immutable evaluation snapshot whose provider authenticity is external; its module documents the Ed25519 primitive as test-lane and not production-approved (`src/business_ai_gateway/phase2/change/trust_registry.py`). Existing `change_ledger.evidence_records` stores JSONB projections, while `dispatch_receipts` stores only selected receipt fields (`db/phase2/005_change_registry.sql`, `db/phase2/016_dispatch_receipt.sql`); neither is the S13 canonical source of signed bytes. Therefore add `change_ledger.private_writer_evidence` as an append-only registry: `evidence_ref text PRIMARY KEY` (nonempty, trimmed); `record_type text` closed to the exact S12 versioned types (`DISPATCH_RECEIPT_V1`, `OUTCOME_EVIDENCE_V1/V2/V3`, `COMPLETION_PROOF_V1`, `POST_COMPLETION_CHALLENGE_V1`, and `POST_COMPLETION_READ_ATTESTATION_V1`); canonical `signed_bytes bytea NOT NULL`; `signed_bytes_sha256 bytea NOT NULL` with length 32; canonical `record_digest text` lowercase 64-hex; the full immutable binding columns `tenant_id`, `company_id`, `organization_ref`, `base_fingerprint`, `change_id uuid`, `claim_generation bigint`, `dispatch_generation bigint`, `call_id uuid`, `dispatch_cas_id uuid`, `operation_kind`, `target_ref NULL`, `pre_version NULL`, `signer_key_id`, `signer_key_version`, `signer_role`, `signer_service_id`, `signer_host_id`, `signed_at`, `verified_at`, and `validator_build_id`; nullable process/session IDs follow the signed type. Non-NULL process identity is canonical lowercase RFC UUID text with supported version/variant bits. Nullable UUID projection IDs, including receipt, outcome-receipt, challenge and completion-proof IDs, reject the all-zero UUID while retaining `NULL` where the signed record type omits that identity. Require exact-type uniqueness by `(record_type, record_digest)` and composite uniqueness needed for attempt binding. Exact signed bytes are the bytes parsed and validated; no JSONB reconstruction, normalization, or replacement is allowed. Reject noncanonical UTF-8/JSON, duplicate keys, unknown/missing fields, wrong domain/version, mismatched digest, scope/CAS/operation/target/version/process binding, unknown or wrong key version/role, signer not authorized for that scope, signature failure, future/stale/revoked key, and rotation-history mismatch before registry insertion. Registry rows and key-version/scope bindings are immutable; key revocation/validity is append-only and checked against both signed time and current validation time. The S13 routines resolve every supplied ref to this relation and recheck record type, digest, all composite identity/CAS/attempt bindings, signer role/key version, and the operation-specific success/no-effect predicates inside the transition transaction. Registry references cannot be created by the writer/admission login.
- Define the trust source separately as `private_writer_signer_key_versions`: `(key_id text, key_version text)` primary key; `public_key bytea NOT NULL CHECK(octet_length(public_key)=32)`; closed `signer_role`; `service_id`, `host_id`; `valid_from`, `valid_until` with `valid_until>valid_from`; `registered_at`; and append-only revocation events keyed by `(key_id,key_version,revoked_at)` rather than mutable key replacement. `private_writer_signer_key_scopes(key_id,key_version,tenant_id,company_id,organization_ref,base_fingerprint)` has a composite primary key and FK to that exact version. Rotation history is represented by immutable predecessor/successor key-version edges and is cycle-free; insertion requires a same-role/service/host predecessor and no public-key reuse. The evidence table has composite FK `(signer_key_id,signer_key_version) → private_writer_signer_key_versions(key_id,key_version)` and the evidence-to-attempt FK `(tenant_id,company_id,organization_ref,base_fingerprint,change_id,claim_generation,call_id,dispatch_generation,dispatch_cas_id) → dispatch_attempts` on an explicit matching unique key. Type-specific checks require receipt evidence to bind one attempt and the exact writer role/process, outcomes to bind the independent verifier role and receipt digest, completion proofs to bind both generations/CAS/process, and challenge/read-attestation records to bind the preceding proof/challenge digests and strictly later verification sequence. Barrier acknowledgements retain their dedicated registry table but use the same signer-version and scope registry; they are not S12 terminal evidence.
- Payload binding is mandatory at every durable level: `private_writer_dispatch_intents.payload_digest` is copied from the locked record and bound to the approved permit/checkpoint; `dispatch_attempts.payload_digest` is copied from that immutable intent; `private_writer_evidence.payload_digest` is populated from the validated signed record (`DispatchReceipt.approved_payload_digest` where applicable). Add the matching exact composite unique key to the attempt and evidence rows so the evidence FK includes `payload_digest`; registration and terminal routines compare the signed digest to the attempt and intent. This closes the adapter's `CallIdentity.payload_digest` and prevents call/CAS replay across a different approved payload.
- Exact FK target map: `dispatch_intents` uses primary key `dispatch_intent_id` and unique `(dispatch_intent_id,change_id,claim_generation,dispatch_generation,call_id,payload_digest)`. `private_writer_permit_bindings` uses unique `(dispatch_intent_id,permit_id,permit_digest)`. `dispatch_attempts` uses unique `(dispatch_cas_id,dispatch_intent_id,change_id,claim_generation,dispatch_generation,call_id,payload_digest,permit_id,permit_digest)` and two FKs: `(dispatch_intent_id,change_id,claim_generation,dispatch_generation,call_id,payload_digest)` to the intent key, and `(dispatch_intent_id,permit_id,permit_digest)` to the issued-permit key. It also uses narrow existing-parent FKs `change_id → records(change_id)` and `(change_id,claim_generation) → dispatch_permits(change_id,generation)`. The admission routine locks those legacy parent rows and compares all copied scope, base, operation, target/version, approval, payload, permit and epoch fields before committing. S13 evidence rows carry `dispatch_intent_id`, `dispatch_cas_id`, `change_id`, both generations, `call_id`, `payload_digest`, `permit_id`, and `permit_digest`; their FK references the exact attempt unique key above. A registration/terminal trigger compares every flattened signed field (tenant, company, organization, base, operation, target/pre-version, approval/permit digests and process/session IDs) against the locked intent/attempt and signer registry. This deliberately avoids FK declarations against nonexistent legacy composite keys while preserving database-enforced identity anchors plus exact locked-row validation.
- The current `private_writer_evidence.record_type` candidate enum includes `DISPATCH_RECEIPT_V1`, `DISPATCH_NO_ENTRY_RECEIPT_V1`, `OUTCOME_EVIDENCE_V1/V2/V3`, `COMPLETION_PROOF_V1`, `POST_COMPLETION_CHALLENGE_V1`, and `POST_COMPLETION_READ_ATTESTATION_V1`. `DISPATCH_NO_ENTRY_RECEIPT_V1` is a distinct signed envelope only for a coordinator-level no-entry fact; it is never an unsigned flag and cannot resolve a possibly-entered call unless the durable COM-entry fence also proves the old owner cannot enter later. `BarrierAcknowledgement` remains only in `writer_barrier_acknowledgements`, never in the S12 attempt-evidence enum.
- Evidence registration checks the key's validity and revocation as of `verified_at`. Terminalization is permitted only in a fresh top-level `READ COMMITTED` transaction; any other isolation fails closed before locks. It sorts all involved `(key_id,key_version)` values lexically, acquires shared locks on those immutable key-version rows in that order, then performs a separate new `READ COMMITTED` statement to read current validity and append-only revocation events. The revocation writer takes the conflicting exclusive lock before appending its event and holds it through commit. That routine accepts no effective-time argument: it assigns `revoked_at` from the database clock after locking, and the event is immutable. Terminalization refuses if any committed revocation row is visible after the locks are held or the key is no longer currently valid; it does not compare `revoked_at` to the transaction start time. The revocation query must use the post-lock statement snapshot, or a pre-wait snapshot could miss the just-committed event. Thus revocation after ingestion but before terminalization invalidates that evidence for terminal use; it is not retroactively deleted or rewritten. Evidence accepted by an already committed terminal transition remains an audit fact, while a later revocation cannot rewrite its past.
- Persist all evidence associations in append-only `private_writer_attempt_evidence(dispatch_cas_id, evidence_ref, evidence_purpose, recorded_at)`, primary key `(dispatch_cas_id,evidence_ref)`, closed purpose enum, and composite FKs to the attempt and canonical evidence registry. A unique partial constraint limits a purpose that is single-valued for one attempt, while causal proof chains (completion → challenge → read attestation → outcome) retain explicit parent evidence refs and may not be overwritten. API `receipt_ref` is only a stable response/lookup projection of the `WRITER_RECEIPT` association; terminal `evidence_ref` is a deterministic projection of the selected terminal proof association, not the only retained evidence. Terminal routines append the complete required evidence set and transition state atomically. `NOT_ACCEPTED` remains absence of an attempt row, not a persisted state.
- **Trusted registry writer is a separate trust principal.** Only a narrowly authenticated LOGIN principal `private_writer_evidence_ingest` may invoke the versioned evidence-registration routine; it has no ledger transition, COM, direct table DML, schema-owner, superuser, `BYPASSRLS`, role-membership or role-administration privilege. Its authenticated identity is derived from a dedicated certificate-mapped `session_user`, not a caller argument. The registration routine may store only a verifier-produced immutable validation result, linked to the original bytes and exact trusted key-version record; general writer/application roles may resolve refs but cannot insert or alter evidence. The validation service must use a production-approved Ed25519 implementation and an authenticated, versioned trusted-identity/key/oracle registry with provenance, key validity/revocation and rotation history. The existing Python reference registry and PostgreSQL test-lane verifier do not satisfy this requirement. The validation service, its signing-key custody, validator build provenance, and authenticated DB identity are a production trust dependency and remain NOT_VERIFIED until security-reviewed and qualified. No design or migration may treat a boolean `signature_valid` supplied by the writer as proof.
- Immutable evidence references are global IDs allocated before ranked locks and acquired in namespace 6 using a type-prefixed, canonical ID key. Registration is idempotent only when ref, type, exact bytes/hash, complete bindings and key ID/version all match; any changed tuple conflicts before disclosure. A lost registration response is reconciled by lookup of the same ref. Evidence insertion and terminal transition may be separate transactions, but any failure after a physical call preserves the unresolved attempt and physical-base hold; no transaction spans external verification, registry network I/O or COM.
- An entered `CONDITIONAL_VERSION_CONFLICT` is not T8 and cannot be stored as `NOT_INVOKED`. Keep the attempt unresolved until the exact method-completion proof and independent no-effect `OutcomeEvidence` validate the same call/CAS and attribute any observed version change to the competing writer. Compare version tokens for equality only; the conflict contract does not assume a sortable or numeric version. Only then, with the inherited T16 operator and recovery-witness signatures satisfying S12 revision-6 independence rules, may one top-level transaction store `FAILED_APPLY`, permanently consume the call ID, and release the hold/reservation under the scope fence. Missing or contradictory evidence/signatures leave the hold and `APPLY_UNKNOWN`; no retry path exists.

### Retained S12 begin-apply transition

S13 does not subsume the earlier `begin_apply` preparation transition into private-writer `admit`: `begin_apply` consumes the issued claim token, moves the record to `APPLYING`, inserts the `NOT_PERMITTED` `(change_id,generation)` permit containing `call_id`, `writer_host`, and `onec_session`, and appends `APPLYING` atomically. After the existing S12 approval/signature issuance path advances that permit from `NOT_PERMITTED` to `PERMITTED`, private-writer `admit` validates the exact identity and performs the existing `PERMITTED → DISPATCHED` CAS while creating the immutable attempt; `mark_invoking` separately gates COM entry. ### Scope epoch and recovery barrier

- Keep lifecycle epoch/state as the authority; do not create a second mutable lifecycle epoch. In addition, maintain a durable base-wide admission-closed flag keyed by authenticated `base_fingerprint`; it is a temporary physical barrier state, not an epoch or authorization source. `close_and_advance` takes namespace 8 before namespace 7, atomically closes admission for that base, compares the supplied expected current scope epoch, computes the successor in the database, closes the requested scope, creates an immutable `barrier_id`, and snapshots every unresolved physical call for that base across all scopes. Persist both the expected-current and computed resulting epoch in the immutable barrier. The resulting epoch is authoritative and is used in the physical acknowledgement. The transaction commits before waiting for the local COM queue or performing writer/service I/O. Admission in any scope sharing the base refuses while the base barrier is open. Replaying the same barrier ID for the same base/scope returns its original immutable snapshot and both epoch fields even if the caller supplies the now-stale expected epoch; the coordinator validates the stored relation `epoch = expected_current_epoch + 1`. A different base/scope binding conflicts.
- Store a `writer_barriers` parent row and one child row per pre-barrier attempt. This materialized set is immutable; progress is monotonic and references validated evidence. No pagination may omit a call. If it cannot be stored or read completely, recovery remains closed and `NOT_READY`.

### Transaction and lock behavior

- Each adapter method uses one fresh top-level `READ COMMITTED` database transaction, set as the first SQL command after `BEGIN`; unsupported isolation fails closed before any fence acquisition. Immediately thereafter start a monotonic five-second transaction deadline (or preserve a shorter caller deadline) and set `SET LOCAL statement_timeout` to the remaining duration before each SQL statement; bound commit by the same remaining deadline. This outer deadline bounds later row/FK/unique waits and commit in addition to the separate five-second cumulative advisory-fence budget. The five-second total is a conservative, unmeasured ceiling; disposable-lane latency and reliability review must validate it before enablement. Timeout remains an indeterminate DB result, rolls back the transaction, and never proves that a physical call did not happen. Commit/rollback completes before returning; no transaction spans COM or a remote call. Qualification ID: `S13-PG-DEADLINE-01`.
- The dedicated blocking scope/global-ID fence helper maps only its own bounded lock-timeout exception to `LEDGER_LOCK_TIMEOUT`. Generic SQLSTATE `55P03` is not sufficient provenance and remains distinguishable from unrelated lock-not-available errors; statement cancellation (`57014`) and deadlock (`40P01`) also fail closed. The adapter must not catch any such error inside a transaction and continue. Qualification ID: `S13-LOCK-ERROR-01`.
- Every global unique conflict domain enumerated in `S13_SCOPE_FENCE_IMPLEMENTATION_DESIGN_2026-10-22.md` uses namespace 6 before row locks or DML, including generated table UUIDs, caller-supplied IDs, and the global composite-primary-key domains `sweep_counters(subject_id,kind)` and `sweep_failures(subject_id,stage)`. The `verify_attempt_log.evidence_id` global primary key is populated from the caller-selected observation UUID by the current verify path (`db/phase2/008_change_hardening_b.sql:1824-1853`). Allocate candidate-generated IDs before the first ranked lock and include their actual lock tuples in the same bounded plan. Domain encoding and collision-safe ordering are specified in the scope-fence design. A top-level transaction that would mutate multiple `(tenant_id, company_id)` scopes must refuse before its first lock; sorted scope batching is unsupported until separately designed and qualified. The canonical advisory rank and `READ COMMITTED` fence order are defined in the scope-fence design; schema-derived SCC order handles FK parents/children, including `targets → records self-SCC → claim_tokens` unless the exact additive schema introduces a cycle. ## Failure modes and rollback

- Lost CAS/admission response: query the same immutable call identity; never create a new call or invoke COM based on an ambiguous response.
- Crash after attempt insert but before invocation transition: only the bound process may claim the one-way transition; after restart, if non-entry cannot be proven, classify unresolved and keep the hold.
- Crash or connection loss after invocation transition: treat as possibly executing; query the writer by stable call ID; never invoke again.
- Barrier acknowledgment or complete call set unavailable: preserve RECOVERING/closed admission and `NOT_READY`; do not clear state by timeout.
- Migration rollback is forward-only: keep the new dispatch route disabled and preserve attempts/evidence. Do not drop records or edit migrations 022–024.
