## 2. Trust boundaries and evidence types

The prototype's canonical JSON hash and synthetic writer receipt prove only what the simulator accepted. Migration 018's receipt requirement is opt-in, and a CT14 marker can be changed through an API writer. Neither a marker's presence nor absence proves application or non-application. A JSON digest does not prove which COM properties were assigned or persisted.

v2.0 requires two independent signed records with different signers and purposes, plus a separately typed `CompletionProof` record for physical-call completion. None can substitute for another, and completion is never inferred from timeout, a missing receipt, or `call_returned=false` alone.

### 2.0 Canonical signed bytes

All three evidence records use closed, versioned JSON schemas and the same serialization rules as `S12-APPROVAL-2`: UTF-8; keys sorted lexicographically; compact `,` and `:` separators; ASCII-only JSON with non-ASCII encoded using the standard JSON backslash-u escape; no floating-point values; decimals represented as canonical strings; timestamps encoded exactly as UTC RFC 3339 `YYYY-MM-DDTHH:MM:SS.ffffffZ` (six fractional digits; no leap-second form); every nullable field present as explicit JSON `null`; reject duplicate keys, unknown fields, invalid Unicode, and noncanonical encodings. The field lists below are the complete required v1 schemas, including explicit nullable fields. A contract or field-semantics change requires a new record version.

Each record uses two deterministic, non-circular byte strings. First, `digest_preimage` is the domain-separation prefix followed by canonical UTF-8 JSON of the complete envelope excluding both its signature field and its digest field (`signed_payload_digest` or `canonical_evidence_digest`). Compute lowercase hexadecimal `record_digest = SHA-256(digest_preimage)`. Second, `signature_preimage` is the same prefix followed by canonical UTF-8 JSON of the complete envelope including the computed digest and excluding only the signature field. The signer computes Ed25519 over `signature_preimage`. The receiver recomputes both byte strings, digest and signature; mismatch rejects the record.

| Record | Exact prefix |
|---|---|
| `DispatchReceipt` | `ERP_MCP_R2:S12:DISPATCH-RECEIPT:v1` followed by one LF byte |
| `OutcomeEvidence` | `ERP_MCP_R2:S12:OUTCOME-EVIDENCE:v1` followed by one LF byte |
| `OutcomeEvidence` (proposed closed v2 schema) | `ERP_MCP_R2:S12:OUTCOME-EVIDENCE:v2` followed by one LF byte |
| `CompletionProof` | `ERP_MCP_R2:S12:COMPLETION-PROOF:v1` followed by one LF byte |
| `BarrierAcknowledgement` (separate S13 physical-writer record; not S12 attempt evidence) | `ERP_MCP_R2:S13:PHYSICAL-WRITER-BARRIER:v1` followed by one LF byte |

The envelope includes and therefore signs its version, scope, all authorization/call or observation claims, signer key ID, key version, role and algorithm. No caller-selected serialization, detached unsigned metadata, or algorithm fallback is accepted. Approval and evidence digests remain distinct domains.

`BarrierAcknowledgement` is a separate closed, versioned S13 record, not one of the three S12 evidence records and not interchangeable with `DispatchReceipt`, `OutcomeEvidence` or `CompletionProof`. Its signature uses UTF-8 canonical JSON with sorted keys, ASCII escaping, compact separators and non-finite numbers forbidden, under the exact S13 domain above; Ed25519 signs that domain prefix plus the canonical body and the detached signature is 64 raw bytes. Its signed tuple includes the complete physical base/scope/resulting lifecycle epoch, immutable barrier ID and origin instance/serving epoch, complete ordered base-wide call set, writer service/host/boot/process identity, independent process-attestation reference, queue epoch, `local_queue_closed=true`, signer key ID/version and `signed_at`. The separate barrier verifier validates the exact signed bytes, key version and process attestation; it does not infer queue closure from the signed boolean alone.

### 2.0.1 Scope-bound identity registry

At verification time, a trusted registry must map `(key_id, key_version)` to an authenticated writer, barrier-signer, verifier or completion-supervisor service identity; authenticated host identity; Ed25519 public key; one purpose/role; allowed tenant/company/organization/base scope; validity interval; revocation status; and rotation history. The v1 purpose mapping is exact: `DispatchReceipt` and `WRITER_CALL_RETURNED` use `writer_receipt`; `OutcomeEvidence` uses `verification_worker`; `INDEPENDENT_SESSION_AND_PROCESS_CLOSED` uses `completion_supervisor`; `BarrierAcknowledgement` uses the `writer_receipt` purpose under a dedicated `barrier_signer` service identity and key pair distinct from `DispatchReceipt` signing; checkpoint signing retains its separate `checkpoint_signer` identity. Barrier signer keys are scoped to the authenticated physical base and every represented organization, and bound to the authenticated writer host/process and immutable barrier-origin tuple. The acknowledgement verifier and its registry-insertion authority are separate from the `OutcomeEvidence` verifier and from writer/application database roles. Only the trusted acknowledgement-verifier path may insert the exact validated acknowledgement bytes; writer/application roles have no direct acknowledgement-registry DML. No one identity or database role may both assert the physical queue state and grant itself authority to accept that assertion. Writer, barrier signer, verifier, completion-supervisor and checkpoint authorities are distinct; other roles retain their existing separate keys and authorities. A completion-supervisor identity is additionally host-scoped to the exact writer host/service it may observe and may attest process/session closure only; it has no 1C mutation, approval, or outcome-verification authority. The verifier checks the registry record against both the signed envelope and expected scope. `writer_service_id`, `writer_host_id`, `verifier_service_id`, `verifier_host_id` and `key_version` are not trusted merely because they are signed. The trusted host supervisor also attests the writer process instance: `writer_process_instance_id` is a cryptographically random, non-reusable service-start UUID bound to the authenticated host boot UUID, service instance, OS process ID and process creation time. A PID alone is never a process identity. Process-instance binding is authenticated by the supervisor identity registered for that host. Runtime registry/supervisor unavailability or an unknown, revoked or mismatched identity fails closed. Actual registry provenance and custody remain external qualification requirements under R-03. The pinned PostgreSQL candidate requires a `writer_receipt` key for acknowledgement registration; this candidate adopts that purpose only for a dedicated barrier-signer identity and key pair. Review D confirmed this identity-to-purpose mapping for the bounded design baseline; trusted ingest/verifier principal qualification remains required.

### 2.1 `DispatchReceipt` — trusted writer attestation

The writer signs a durable, immutable, versioned receipt. The following are the complete required v1 fields; no unlisted field is accepted:

- **Scope and target:** `receipt_version`, `tenant_id`, `company_id`, `organization_ref`, authenticated `base_fingerprint`, `target_class`, nullable-by-operation `expected_target_ref` and `expected_pre_version`.
- **Authorization:** `change_id`, `request_id`, `claim_generation`, `approval_digest_version`, `approval_digest`, `auth_epoch`, `permit_id`, `permit_digest`.
- **Physical call:** `receipt_id`, `call_id`, `dispatch_generation`, `dispatch_cas_id`, `writer_service_id`, `writer_host_id`, `writer_process_instance_id`, nullable `onec_session_id`, nullable `onec_session_instance_id`, `operation_kind`, `started_at`, `write_invocation_stage`, `call_returned`, nullable `returned_at`, `result_class`, nullable returned target/version, nullable `no_effect_evidence_digest`, and nullable bounded `error_family`.
- **Mapping/configuration:** `mapping_version`, `configuration_fingerprint`, `approved_payload_digest`, `mapped_property_manifest_sha256`, and `COM_operation_manifest_sha256`.
- **Signature:** `signer_key_id`, `key_version`, `signer_role=writer_receipt`, `algorithm=Ed25519`, `signed_payload_digest`, and signature.

The property manifest hashes the normalized ordered assignments prepared for COM (1C property, type, value or value digest), including write mode, property-setting method, and tabular-section changes. The operation manifest binds the selected method/write mode, target, and expected version. The receipt attests what the authenticated writer prepared and observed at its boundary; it does not independently prove persisted 1C state.

For a post-CAS refusal proven before entering the mutating COM method, the signed `DispatchReceipt` is the stage-proof record: `write_invocation_stage=NOT_INVOKED`, `result_class=PRE_WRITE_NO_EFFECT`, `call_returned=false`, null return fields, and a non-null operation-specific `no_effect_evidence_digest`. For every other result class this field is explicit null. Its signature binds `dispatch_cas_id`, `writer_process_instance_id`, exact 1C session instance when available, scope, generation and call. The invocation guard must persist a one-way “COM method not entered” fact for that process instance/call before this receipt is committed. This receipt is mandatory to take T8 after CAS; if it or the guard evidence is missing, not durable, or disagrees, the state remains `APPLY_UNKNOWN` with the hold. Pre-CAS refusal remains `PRE_DISPATCH` and creates no dispatch receipt. A conditional-write conflict returned from inside an already-entered mutating COM method is a different history: record `write_invocation_stage=ENTERED`, `call_returned=true`, `result_class=CONDITIONAL_VERSION_CONFLICT`, null successful return target/version, and `no_effect_evidence_digest=null`; never take T8. If the entered method does not return or its result is ambiguous, classify it as `POST_START_UNKNOWN`. Keep `APPLY_UNKNOWN` and the hold until the exact `CompletionProof` establishes method completion and independent `OutcomeEvidence` establishes that the governed call had no effect; any observed target-version change must be attributed to the competing actor, not this call. Only then may the ledger atomically commit the evidence-bound `FAILED_APPLY` terminal transition through the inherited T16 two-person resolution: distinct operator and recovery-witness signatures, neither signer the requester, and the approver-disjointness rule from the applicable S12 revision-6 clause. The same transaction permanently consumes the call ID and releases the hold/reservation under the scope fence. If the schema or approved transition does not yet implement that exact evidence and signer guard, keep the call unresolved and held; never substitute an operator assertion or refusal code. Any ambiguity stays unresolved and is never retried.

### 2.2 `OutcomeEvidence` — independent read-only verifier

The verifier uses a separate service/host identity, Ed25519 key, and read-only authority. It must not receive the writer key, perform COM mutations, confirm success from a marker, or reuse the writer's transformation/mapping implementation as its oracle. The following are the complete required v1 fields; no unlisted field is accepted:

- **Correlation:** `evidence_version`, scope tuple, `change_id`, `claim_generation`, `call_id`, nullable `dispatch_receipt_id`, and `approval_digest`.
- **Verifier identity:** `verifier_service_id`, `verifier_host_id`, `signer_key_id`, `key_version`, `algorithm=Ed25519`, `role=verification_worker`.
- **Observation:** `observed_at`, `read_session_id`, `target_ref`, pre/observed version tokens, document posting state, canonical field snapshot digest, and canonical lines digest.
- **All movements:** complete normalized multiset of register movements, registrar, versioned register catalogue, count and digest by register, and total `movement_multiset_digest`.
- **Comparison and attribution:** expected/observed effect digests, field and movement matches, version relation, reader health, observation completeness, effect presence/identity, completion proof class, attribution result and evidence reference, and explicit uncertainty list.
- **Signature:** canonical evidence digest and verifier signature.

The following is the mandatory cross-record success predicate; every equality is exact and evaluated before `VERIFIED`:

| Operation | Signed `DispatchReceipt` constraints | Signed `OutcomeEvidence` constraints |
|---|---|---|
| `CREATE_DRAFT` | `expected_target_ref=null`; `expected_pre_version=null`; successful `result_class`; writer-derived `returned_target_ref` and `returned_version` are present and were obtained from the qualified COM operation result, never caller input. | `pre_version=null`; `target_ref=receipt.returned_target_ref`; `observed_version=receipt.returned_version`; independent attribution binds the observed effect to this governed call. If attribution is ambiguous, return `TRIAGE_REQUIRED`. |
| `POST` / `UNPOST` successful result only | `expected_target_ref=approved_preimage.target_ref`; `expected_pre_version=approved_preimage.pre_version`; `returned_target_ref=approved_preimage.target_ref`; `returned_version` is present and writer-derived from the qualified COM operation result. | `target_ref=receipt.returned_target_ref=approved_preimage.target_ref`; `pre_version=approved_preimage.pre_version=receipt.expected_pre_version`; `observed_version=receipt.returned_version`; `observed_version != approved_preimage.pre_version`; independent attribution binds the effect to this call. |
| `POST` / `UNPOST` conditional conflict after method entry | `expected_target_ref=approved_preimage.target_ref`; `expected_pre_version=approved_preimage.pre_version`; `write_invocation_stage=ENTERED`; `call_returned=true`; `result_class=CONDITIONAL_VERSION_CONFLICT`; returned target/version null; `no_effect_evidence_digest=null`. | Exact call/receipt/CAS binding; approved `pre_version` retained; observed state and oracle evidence show no effect attributable to this call and attribute any version change to the competing writer. Do not apply the success equality requiring a new version. Require matching completion proof, independent no-effect evidence, and the inherited T16 two-person resolution before the evidence-bound `FAILED_APPLY` transition. |

For the conditional-conflict row, the candidate envelope contract requires `OutcomeEvidenceV3` to bind the exact completion-proof digest, post-completion challenge ID, and separate read-attestation digest. Its signed observation must set `observation_complete=true`, `effect_presence=ABSENT`, `effect_identity=NO_GOVERNED_EFFECT`, `attribution_result=COMPETING_WRITER`, and `version_relation=DIFFERENT_COMPETING_WRITER`; `observed_version` must differ from the approved pre-version; `attribution_evidence_ref` must be non-empty; and `uncertainties` must be empty. Version tokens are compared for equality only; the contract does not assume that tokens are ordered or numeric. The V3 registry must resolve the exact document-shape, configuration, oracle, and expected-effect-schema artifacts. A distinct process-attested `read_attestor` signature must bind the random challenge nonce and query-plan digest to the source-response digest, exact V3 observation claims, and durable sequence above the supervisor-signed floor. These are still trust claims requiring measured attestor implementation and oracle qualification. The recovery adapter must load the exact immutable receipt/outcome/completion/challenge/read-attestation records and call `validate_conditional_conflict_terminal_record_set` before the transition transaction. This wrapper verifies signatures, scope, process/oracle binding, causal chain and structural conflict predicate; SQL must recheck all immutable IDs/digests atomically with active serving epoch, T16 signer and hold rules. V1 and V2 remain insufficient for an entered conditional conflict.

For all rows, additionally require exact scope, operation, generation, `call_id`, `dispatch_cas_id`, approval digest, permit, receipt ID, signer roles/keys, signature, mapping and configuration bindings. Missing, unknown, caller-derived, stale, contradictory or unverifiable target/version/result values cannot support `APPLIED` or `VERIFIED`. A successful result class is operation- and topology-specific and must be enumerated in the qualification manifest; an unlisted result class fails closed to `APPLY_UNKNOWN`/`TRIAGE_REQUIRED` as appropriate. An in-method conditional conflict is not a successful-result row: it follows the post-start completion and independent no-effect reconciliation rule in §2.1, never the `NOT_INVOKED` path.

The expected movement multiset is defined by an independently maintained, versioned operation-rule matrix for the qualified document shape. CT14's observed movements do not justify a universal fixed movement count. Draft creation expects an unposted document and no unexpected registrar movements; posting expects the qualified posted state and complete allowed movements; unposting expects the unposted state and the qualified treatment of prior movements.

### 2.2.1 Proposed `OutcomeEvidence` v2 oracle and expectation binding

Because the v1 envelope is closed, do not add fields to v1. The proposed v2 envelope is the complete v1 field set plus signed `document_shape_revision`, `configuration_fingerprint`, `oracle_id`, `oracle_version`, `oracle_digest`, and `expected_effect_schema_version`; `expected_effect_digest` is retained exactly once from v1 and now explicitly hashes the canonical expected field, line, posting-state and normalized movement multiset for this operation and approved pre-image. The v2 signature uses the v2 domain-separation prefix above. The new references identify the independently maintained operation-rule matrix and source revision and pin the qualified 1C document shape/configuration. A trusted immutable registry resolves each identifier/digest to the reviewed artifact; unknown, changed, mismatched or superseded references fail closed. Qualification freezes the accepted oracle/configuration/document-shape tuple; same-version content replacement is prohibited. New operations cannot downgrade to v1 after v2 acceptance; historical v1 evidence is never silently reinterpreted as carrying v2 provenance.

### 2.3 Completion proof

`CompletionProof` is a separate signed record with required fields `proof_version`, `completion_proof_id`, full scope tuple, `change_id`, `claim_generation`, `dispatch_generation`, `dispatch_cas_id`, `call_id`, `operation_kind`, `writer_process_instance_id`, nullable `onec_session_instance_id`, `proof_class`, `source_service_id`, `source_host_id`, `source_process_instance_id`, nullable `source_session_instance_id`, nullable `observed_session_instance_id`, `evidence_ref`, `evidence_digest`, `observed_at`, `signer_key_id`, `key_version`, `signer_role`, `algorithm`, `canonical_evidence_digest`, and `signature`; nullable fields are explicit JSON null. `writer_process_instance_id` and `onec_session_instance_id` identify the process/session whose call completion is claimed; `source_*` fields identify the process/service/host/session signing the proof; `observed_session_instance_id` records the exact 1C session observed by a supervisor. `source_session_instance_id` identifies the source service's own session and is not interchangeable with the observed 1C session.

1. **`WRITER_CALL_RETURNED`:** the exact registry-authenticated writer process attests that its COM mutating invocation returned, binding `call_id`, `dispatch_generation`, non-reusable `writer_process_instance_id`, service/host, 1C session instance, operation and return boundary. Require `signer_role=writer_receipt` and validate `source_process_instance_id == writer_process_instance_id == DispatchReceipt.writer_process_instance_id` (or the dispatch-attempt process binding when the receipt is not yet durable); `source_service_id` and `source_host_id` must also equal the writer service and host bound to that attempt. Where a 1C session instance is available, `observed_session_instance_id` must equal it. This class proves completion only for the exact COM method and topology qualified to have no deferred server-side application after return. It does not by itself prove the effect or its attribution; CT14 does not establish this property for client-server topology.
2. **`INDEPENDENT_SESSION_AND_PROCESS_CLOSED`:** an independently registry-authenticated host/session supervisor attests that the exact writer `writer_process_instance_id` and corresponding `onec_session_instance_id` are closed and that the platform can no longer execute or resume that invocation. Here `source_*` identifies the supervisor, and must validate to a registered `completion_supervisor` service/key/process identity with `signer_role=completion_supervisor`; it is intentionally distinct from the writer. `observed_session_instance_id` must equal the 1C session instance bound to the call when available. The signed evidence reference identifies the supervisor's authoritative closure observation for the exact writer process/session instances. A host process exit alone, a recyclable PID, a client disconnect, or a timeout is insufficient.

Each proof signs its proof class, source identity, evidence reference/digest, observed time, operation, non-reusable writer process/session instances, supervisor process identity where applicable, and common scope/change/generation/CAS/call binding. The ledger accepts it only after registry and signature validation. If neither class can be established, retain `APPLY_UNKNOWN`, `POSSIBLY_EXECUTING`, locks, reservation and base-wide hold. A complete read-back does not prove completion. Forced termination is prohibited. If the platform cannot distinguish failure before write from an already-started call, classify it as `POST_START_UNKNOWN`.

## 3. State, retry, and fencing rules

| Observed boundary | Classification and ledger behavior | Retry/hold rule |
|---|---|---|
| No permit or `DISPATCHED` compare-and-set (CAS) | `PRE_DISPATCH`; cancellation is safe only with durable proof that dispatch was impossible. | No physical call occurred. |
| COM validation refuses before entering the mutating method, with signed stage proof and operation-specific no-effect evidence | `PRE_WRITE_NO_EFFECT`. | T8 may release reservations and locks under the frozen transition rules. A refusal code alone is insufficient. |
| Entered conditional COM method returns `CONDITIONAL_VERSION_CONFLICT` | The physical method was entered; never `PRE_WRITE_NO_EFFECT` and never T8. | Keep `APPLY_UNKNOWN`/hold until exact completion proof, independent no-effect attribution, and inherited T16 operator-plus-recovery-witness signatures validate; then an evidence-bound atomic `FAILED_APPLY` transition may release the hold and reservation. If any evidence or signer is absent, remain held. |
| Timeout, disconnect, cancellation, crash or unclassified error after write may have started | `POST_START_UNKNOWN`; ledger enters `APPLY_UNKNOWN`, call ownership `POSSIBLY_EXECUTING`. | Do not retry. Keep target/base locks, lease and reservations; retain base-wide hold pending completion and reconciliation. |
| Writer reports success but receipt persistence/SQL acknowledgment is lost | `RECEIPT_PERSISTENCE_UNKNOWN`. | Do not issue another physical call; recover evidence or reconcile. |
| Receipt exists, independent verification is pending | `APPLIED` only with sufficient writer completion/result evidence; remains `NOT_VERIFIED`. | Maintain target exclusivity until independent read-back. |
| Full observation shows no effect but physical completion is unproven | `APPLY_UNKNOWN`. | Do not release base hold or permit a new dispatch. Missing marker/row or elapsed deadline is not proof of absence. |
| Effect exists but cannot be attributed to this `call_id` | `TRIAGE_REQUIRED`; attribution remains unproven. | No automatic `PROVEN` attribution. Any exceptional resolution requires the separately governed two-person path. |

For every governed operation, the server sets a mandatory receipt policy by operation type; callers cannot opt out. The durable dispatch intent and requirement are server-authoritative and atomically bound to the allowed state transition. Scope `(tenant, company, organization, base_fingerprint)` binds approval, target, permit, call, receipt and outcome evidence; any mismatch fails closed.

Every `claim_generation` has one permitted `call_id`. Ledger CAS `PERMITTED → DISPATCHED` is durably recorded before invoking COM. A duplicate request for that call returns the existing state/evidence and never invokes COM again. A new generation cannot bypass an unresolved earlier physical call. A post-start error, unresolved result or missing receipt never becomes `FAILED_APPLY` merely because a deadline passed.

In the local in-memory fixture, interruption after `DISPATCHED` but before the writer-invocation counter is consumed recovers to `APPLY_UNKNOWN` with the base hold retained and invocation count zero. The fixture has no signed supervisor no-invocation event or API to release that hold; it deliberately leaves resolution to a future qualified recovery path. This fail-closed terminal state is not production recovery evidence.

`APPLIED` requires sufficient writer completion/result evidence plus the required `DispatchReceipt`; `VERIFIED` requires separate independent `OutcomeEvidence`. Writer receipt, verifier evidence and checkpoint signing use separate Ed25519 identities. Key purpose, version, role, scope and signer are checked. Receipt/audit persistence failure after the physical call fails closed and preserves the unresolved hold.

### Proposed writer-port and terminal-interface clarification — 2026-10-23 (design-only; no operational authority)

This clarification is a proposed response to the exact-hash review findings; it is not yet approved or runtime-qualified.

- The private coordinator passes a typed `InvocationContext` only after its one-time S12 dispatch CAS wins. It binds the dispatch CAS, service instance/epoch, host, full scope/call/operation/generation, target/pre-version, permit ID/digest, authority epoch, ticket `digest_set_hash`, and a distinct approved payload digest. The digest-set hash is not a substitute for the approved payload digest.
- The physical writer authenticates the process independently and consumes a durable one-way per-call entry guard immediately before the mutating COM method. It repeats entitlement, permit signature/expiry/revocation, authority epoch, kill-switch, authenticated base fingerprint, target/pre-version and generation checks at that boundary. A context object or caller field alone grants no authority.
- The COM writer returns the original signed `DispatchReceipt` bytes. A trusted receipt registry rejects duplicate JSON keys, noncanonical bytes/identifiers, wrong domain/version, untrusted key or mismatched process/CAS/scope before constructing the parsed evidence envelope; it stores the exact immutable receipt and returns its reference. PostgreSQL receives the immutable reference, not a `jsonb` reconstruction of signed bytes.
- Persisting a writer receipt does not establish success or release the physical-base slot. An independent read-only verifier must bind that receipt to operation-specific `OutcomeEvidence` and a matching `CompletionProof`. A dedicated database transition rechecks the immutable IDs/digests and all §2.2 success equalities, then atomically records the terminal ledger state, permanently consumes the call ID, and releases the slot. Entered conditional conflict remains on its separate no-effect/T16 path.
- `PRE_WRITE_NO_EFFECT` after the database invocation reservation is terminal only if a process/CAS-bound durable physical guard proves the mutating COM method was never entered and makes every later entry for that attempt impossible. Otherwise retain `APPLY_UNKNOWN` and the hold.

### Appendix A — Authorization freshness at the last pre-COM boundary

The authenticated writer revalidates the current operation kind, exact scope, target version, `change_id`, claim generation, one-time approval and approver/requester entitlement dependencies, approval expiry, permit validity/signature, key validity/revocation, and kill-switch state immediately before the durable `PERMITTED → DISPATCHED` CAS. It repeats the authority/permit/kill-switch check immediately before invoking COM. For `POST`/`UNPOST`, the qualified physical operation must enforce the approved pre-version as a conditional write/version precondition in the same 1C serialization boundary as the mutation. For `CREATE_DRAFT`, the writer must prove absence/uniqueness under the qualified 1C boundary before creation. A separate read followed by an unconditional mutation is insufficient. If the platform/API cannot provide a qualified atomic precondition, a separately reviewed serialization mechanism must exclude all competing writers for the complete check-and-write interval; if neither can be proven, the operation remains disabled. If the writer detects a mismatch, revocation, expiry or unavailable authority before entering the mutating COM method, it refuses invocation and may use only the signed `NOT_INVOKED` T8 proof above. If the conditional version check rejects after that method has been entered, record an invoked conditional-conflict result and use the post-start completion/no-effect reconciliation path; do not classify it as `NOT_INVOKED` or release the hold from the refusal code alone. An undispatched permit is invalidated when any bound entitlement dependency or authority epoch changes. The CAS records an authorized dispatch attempt before the physical call; it does not itself prove that COM was entered.

If the final pre-call check refuses after the CAS, the change may take the inherited T8 `PRE_WRITE_NO_EFFECT` path only through the signed `DispatchReceipt` variant defined in §2.1, bound to the exact CAS/process/session and proving the COM mutating method was never entered; the per-call writer guard must prove no second invocation can run. The refusal receipt, terminal no-effect state and audit event commit atomically; only then may the locks, lease and reservation be released. If a conditional version conflict is instead detected inside an already-entered COM method, record `write_invocation_stage=ENTERED` and never use T8. Require method completion evidence and independent no-effect evidence for the exact call; until both are validated and the separately authorized no-effect resolution commits, retain `APPLY_UNKNOWN` and the base-wide hold. If that proof is unavailable, malformed, or not durably recorded (including a writer crash after CAS), the outcome is `APPLY_UNKNOWN` and the base-wide hold remains. This does not permit retry under the same call or generation. The narrow revocation race after the final authority check is an explicit system limitation; no atomicity between an external identity provider and a physical COM operation is claimed. Qualification must cover both a pre-entry refusal with exact `NOT_INVOKED` receipt/T8 expectations and an in-method conditional conflict with `ENTERED` stage, completion proof, independent no-effect evidence, preserved hold while either is absent, and no second call.

### Appendix B — Relational and transaction invariants

The eventual additive schema must enforce, rather than merely document, these composite relationships. Every key contains the immutable `(tenant_id, company_id, organization_ref, base_fingerprint, change_id, claim_generation, call_id)` scope where applicable; permit/intent rows may use the prefix that exists before call assignment, with a unique parent key for the final `call_id` binding.

- One immutable dispatch-intent row and one `call_id` per `(tenant_id, company_id, change_id, claim_generation)`; the intent binds `dispatch_generation` and `operation_kind`. A separate immutable dispatch-attempt/CAS record binds `writer_process_instance_id` and nullable `onec_session_instance_id` before the physical call. Both have unique scope-bound parent keys. A call ID cannot be reused across generations or scopes; process-instance IDs identify one service lifetime and may legitimately bind multiple distinct calls in that lifetime.
- The permit references that exact intent/generation/scope by composite foreign key. The dispatch-attempt/CAS record references the intent and stores the authenticated process/session instance binding. Receipt, outcome and completion-proof records reference that exact attempt and parent tuple with composite foreign keys or equivalent database-enforced constraints; the completion-proof foreign key includes `dispatch_cas_id`. Caller-supplied UUID equality alone is insufficient. The ledger verifies a completion proof's writer process/session instance against exactly one attempt and, when present, the receipt before accepting it.
- At most one immutable `DispatchReceipt` per call tuple. `OutcomeEvidence` and `CompletionProof` are immutable, uniquely identified, and cannot attach to any other scope/generation/call. Evidence may be appended as observations, but a terminal state transition references one exact validated evidence ID.
- A database transition guard prohibits `APPLIED` or `VERIFIED` for a governed operation unless its matching required `DispatchReceipt` exists and is valid. `OutcomeEvidence.dispatch_receipt_id` may be null only while the record remains unresolved (`APPLY_UNKNOWN`/`TRIAGE_REQUIRED`) because no receipt was durably recorded; it cannot support `APPLIED` or `VERIFIED`. Pre-dispatch refusals with proof of no dispatch have no receipt and cannot enter `APPLIED`.
- `FAILED_APPLY` after an entered conditional-write conflict is allowed only with the exact `DispatchReceipt` (`ENTERED`, returned conditional conflict), matching `CompletionProof`, independent signed `OutcomeEvidence` proving no governed effect and attributing any observed version change to the competing actor, and the inherited T16 two-person signatures (operator plus recovery witness, subject to the revision-6 independence rules). The transition, evidence/signer references, permanent `call_id` consumption, and hold/reservation release commit atomically. A timeout, writer refusal code, marker absence, or unlinked read-back cannot set `FAILED_APPLY`; without every proof the state remains `APPLY_UNKNOWN` and held.
- Receipt policy is derived from the immutable governed operation kind and is not caller-writable. All three v2.0 operations require it; there is no legacy or opt-out path for this operation class.

Dispatch follows the inherited S12 checkpoint order exactly: (1) one database transaction atomically persists `APPLYING`, dispatch intent, mandatory policy, generation/call ownership and pre-image; dispatch remains `NOT_PERMITTED`; (2) write the signed external checkpoint covering that committed head and read it back; (3) issue the generation-bound permit only after successful checkpoint read-back; (4) the writer revalidates authority and atomically commits the `PERMITTED → DISPATCHED` CAS with its audit event; and (5) after the CAS, rechecks authority immediately before invoking COM. The checkpoint covers the intent/ownership head, while the permit binds the subsequent CAS and call identity; no claim is made that the external checkpoint already contains the later CAS. Each database transaction commits before any external checkpoint or COM call as applicable; no database transaction or row lock is held across checkpoint I/O or COM. Receipt/evidence insertion and the associated state/audit transition are atomic within the database. If persistence fails after dispatch, keep the unresolved hold and recover idempotently; never repeat the physical call. Database constraints and triggers fail closed on cross-scope/generation attachment or missing mandatory evidence.
