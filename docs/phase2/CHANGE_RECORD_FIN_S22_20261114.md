# FIN-S2.2 — approval-page decision contract correction

## Scope

Tighten the approval-page service-port annotation to match the value the handler already validates and accepts: `ApprovalDecision`.

## Finding and change

`ApprovalServicePort.submit_decision` was annotated as `Result[Any, ErrorCode]`, allowing implementations to appear contract-compatible while returning an arbitrary value. The ASGI handler, however, already fails closed unless the service returns an `ApprovalDecision` bound to the requested change, decision, session, principal, person, and scope. The protocol now declares `Result[ApprovalDecision, ErrorCode]` to make that existing runtime contract explicit to implementers and static reviewers.

No behavior, authorization rule, route, listener, database, or production binding changed. This does not make the approval service production-qualified or connect S16 to a writer.

## Evidence and remaining acceptance

- Source inspection: `src/erp_mcp_s16/approval_page.py` declares the port result as `Result[ApprovalDecision, ErrorCode]`; the request handler checks the result value is exactly `ApprovalDecision` before returning success.
- Contract reference: FIN-S2.2 requires a bound decision result and fail-closed approval behavior.
- No tests, checks, build, CI, migration, database, listener, or 1C operation was performed. Behavioral regression evidence is `NOT_RUN` under operator rule 4. FIN-S2.2 remains in progress and unaccepted.

## Follow-up implementation — parse the ticket for both approval methods

Source review found `parsed_ticket` was initialized only in the GET preview branch, while the POST decision branch later compared the successful `ApprovalDecision.change_id` against it. A valid POST could therefore persist the decision and then raise `UnboundLocalError` while building the response. Ticket parsing and canonical UUID validation now happen once before method dispatch, so both GET and POST branches use the same validated UUID. The S16 acceptance map now requires a successful decision POST to return its bound success response.

The regression is `NOT_RUN` under operator rule 4. This is source-level progress only; FIN-S2.2 remains `PARTIAL` and unaccepted.

## Follow-up implementation — bound service-supplied display text

Source review found that `confirmation_phrase` was rendered into the approval page after only a non-empty string check; the HTML input's `maxlength=256` does not constrain the response generated by the server. An oversized phrase could inflate the page, while a lone Unicode surrogate could fail UTF-8 response encoding. The page now rejects confirmation phrases longer than 256 characters, containing control characters, or not strictly UTF-8 encodable. General display text validates UTF-8 encodability and substitutes a fixed placeholder for invalid text. The S16 coverage map includes malformed service values.

This is source-only evidence. The focused malformed-service regression remains `NOT_RUN` under operator rule 4; FIN-S2.2 remains `PARTIAL`, and no live browser, listener, database, or 1C operation is claimed.

## Follow-up implementation — malformed ASGI header container

Source review found the approval app's header parser handled malformed header entries but omitted `TypeError` from its failure boundary. A malformed ASGI scope such as `headers=None` could therefore escape instead of returning the fixed schema refusal. The parser now maps this malformed container to `SCHEMA_INVALID`; the S16 acceptance map includes `headers=None` and non-byte header entries, with the expectation of zero approval-service calls.

This is source-only evidence. No tests/checks were run under operator rule 4; FIN-S2.2 remains `IN_PROGRESS` and unaccepted.

## Follow-up implementation — reject malformed ASGI scope containers

Source review found the approval app called `scope.get()` before validating the ASGI scope object. A `None`, list, or other non-dict value could therefore escape the intended fixed-refusal boundary before authentication or service dispatch. The app now returns `SCHEMA_INVALID` with HTTP 400 before reading any scope fields or calling either dependency. The S16 acceptance map explicitly requires this malformed-scope case and zero authenticator/service calls.

This is source-only progress. The regression remains `NOT_RUN` under operator rule 4; FIN-S2.2 remains unaccepted, and no listener, browser, database, or 1C operation is claimed.

## Follow-up implementation — validate approver session and decision response

Source review found that the approval app accepted a role container by membership alone and showed a success page after checking only part of the returned `ApprovalDecision`. The app now requires exact approver identity, role-container, epoch, and scope shapes before service dispatch. After a decision call, it validates the ticket/action/session/approver/scope binding, version, digest formats, and future-aware expiry before showing success; malformed results map to a fixed refusal. The S16 acceptance map records both cases.

This is source and contract evidence only. The focused ASGI/session/service regressions are `NOT_RUN` under operator rule 4; FIN-S2.2 remains unaccepted. No listener or production binding was enabled.

## Follow-up implementation — reject malformed approval references and CSRF tokens at ingress

Source review found that the page bounded `decision_ref` only by maximum length and passed arbitrary CSRF-token text to the approval service. The form boundary now requires the same 32–512 character reference alphabet used for issued references and a canonical 64-character lowercase hexadecimal CSRF token before calling the service. The S16 coverage map records that malformed values receive a fixed schema refusal with zero approval-service calls.

This is source and contract evidence only. The focused form/service-call regression is `NOT_RUN` under operator rule 4; FIN-S2.2 remains unaccepted. No listener or production binding was enabled.
